Write down the work, then let agents pick it up. Each <Tooltip tip="A piece of work written as a Markdown file in .hivemind/, which you and your agents read and update." cta="Glossary" href="/glossary#issue">issue</Tooltip>
is a Markdown file in the project, so the Issues board updates as an agent works.

<AgentPrompt description="Paste this into your coding agent to start tracking this project's work as Hivemind issues." page="issues">{`
Turn on Hivemind issues in this project and file the first ones.

1. Check Hivemind is installed: \`hive --version\` prints a version.
2. Ask me for a prefix for issue ids: 2 to 10 capital letters or digits, starting with a letter (for example WEB).
3. In the project folder, run \`hive init --prefix <PREFIX>\`. It adds the .hivemind/ folder, agent skills and a CLAUDE.md section. If I only want the issues, use \`hive init --prefix <PREFIX> --no-agentic\` instead.
4. Ask me for up to five pieces of work. For each, run \`hive new "<title>" --ac "<criterion one> || <criterion two>"\`. The || separates acceptance criteria.
5. Check: \`hive list --json\` lists them, with ids <PREFIX>-1, <PREFIX>-2 and so on.

Do not commit anything without asking me. At the end, show me the ids and titles, and tell me that the work button on an issue card in the Issues tool starts an agent on it.
`}</AgentPrompt>

## Turn issues on

<Tabs>
  <Tab title="In the app">
    1. Press **Add**, choose the **Tools** tab, then **Issues**.
    2. Type an **Issue prefix**, such as `MYP`, and press **Set up issues**.
    3. Check: the Issues tile shows an empty board.
  </Tab>
  <Tab title="In a terminal">
    1. In the project folder, run `hive init --prefix MYP`.
    2. Check: a `.hivemind/` folder now exists.

    `hive init` also adds agent skills and a section in `CLAUDE.md`. For the issues alone, add
    `--no-agentic`.
  </Tab>
</Tabs>

The prefix is 2 to 10 capital letters or digits, starting with a letter. Issue ids are `MYP-1`,
`MYP-2`, and so on.

## File an issue

To file one, run `hive new` with a title. `--ac` adds acceptance criteria, the checks that say the
work is done. `||` separates them:

```bash
hive new "Fix token expiry" --ac "boundary test passes || manual check passes"
```

Check: `hive list --state todo` or the board shows it. Other everyday commands:

```bash
hive show MYP-1
hive update MYP-1 --assignee claude --assignee-type agent
hive close MYP-1                  # done; --reason "…" makes it cancelled
hive reopen MYP-1                 # back to todo
```

## Hand an issue to an agent

1. On the Issues board, press **work** on a card. In an open issue, press **Work on this**.
2. If the issue needs a word from you first, a dialog says why. See [Before work starts](#before-work-starts).
3. Read the agent's task, made from the issue, and press **Send**.
4. Check: the agent's tile opens in a frame of its own, on a git worktree of the branch
   `MYP-42-<title>`, and the issue moves to In progress with that branch on it. In a folder that
   isn't a git repository, the agent starts in the workspace's frame instead.

From a terminal or an agent, `hive ctl spawn --issue MYP-42` does the same. The agent follows the
steps below and ticks each criterion on the board.

An agent started with `hive init`'s skills follows these steps:

<Steps>
  <Step title="Read">
    `hive show MYP-42 --json`: the issue and its acceptance criteria.
  </Step>
  <Step title="Claim">
    `hive ctl set-state MYP-42 in_progress`, and it assigns itself.
  </Step>
  <Step title="Plan">
    `hive ctl add-comment MYP-42 "plan: …"`.
  </Step>
  <Step title="Work">
    After each criterion, `hive ctl mark-acceptance MYP-42 <n>`, counting from 0.
  </Step>
  <Step title="Check">
    It runs the tests and build, and commits with the issue id.
  </Step>
  <Step title="Hand back">
    Finished, it runs `hive ctl complete MYP-42`: the work is checked, the branch pushed and the PR
    opened, and the issue moves to review. Otherwise it ends with `hive ctl set-state`:
    `in_progress --note` or `cancelled --note`.
  </Step>
</Steps>

### Pull requests

`hive ctl complete` opens the PR with the GitHub CLI, so `gh auth login` once on the machine the
agent runs on. While an issue's PR is open, the app reads it from GitHub every 3 minutes:

- **Merged:** the issue moves to Done, and its note says how to remove the worktree
  (`hive pr cleanup MYP-42`).
- **Closed without merging:** the issue goes back to In progress, and you get a notification.
- **Changes requested or checks failing:** a badge on the card. In the issue, **Address review**
  or **Fix CI** starts an agent with the review comments or the failing checks.

Working from a fork works with no setup: the branch is pushed to the remote you can push to (your
fork) and the PR opens on the repository it was forked from, as `owner:branch`. To choose
yourself, set `pr_push_remote` (a git remote) and `pr_repo` (`owner/repo`) in
`.hivemind/config.yaml`.

To only move finished work to review, with no PR, set `on_complete: review` in
`.hivemind/config.yaml`. Every setting and `hive pr` command is in the
[CLI reference](/cli#issues).

`.hivemind/.agent.md` sums up the open issues, so a new agent session reads one file.
`hive agent context` writes it again.

### Before work starts

Starting work asks first when the issue may not be yours to start. It asks on **work**, on a drag
into an in-progress column, and on `hive ctl set-state … in_progress`, `hive update --state` or
`--status` into progress, `hive ctl spawn --issue` and `hive ctl workflow`.

| It says | Because | You can |
|---|---|---|
| Assigned to nobody | the tracker has no assignee | **Assign to me and start**, **Start anyway** |
| Assigned to someone else, or already in progress by them | the tracker's assignee isn't you | **Start anyway**, **Assign to me and start** |
| Already done or cancelled | it is closed | **Reopen and start** |
| Not in the active sprint | it is in the backlog or a later sprint | **Start** |
| Blocked by another issue | a `blocked-by` link to an issue that isn't done | **Start anyway**, **Open** the blocker |
| Flagged | the tracker flags it as an impediment | **Start anyway** |
| You may not move or be assigned it | the tracker's permissions | **Start locally only** |
| Its parent is done | a sub-task of a closed issue | **Start** |
| Another install is on it | someone else's hivemind claimed it | **Start anyway** |
| An agent here is already on it | a tile was started on this issue | **Focus that tile**; this one can't be started past |

An issue kept only in this workspace is checked for the closed, blocked, parent and agent rows.
**Don't warn me for unassigned issues in this workspace** turns off the first row for that board.
**Assign to me** needs the tracker's plugin running in the app or `hive host`.

From the CLI the same checks exit 7 with `NEEDS_CONFIRM`, each in `warnings`. Ask the person, then
run the command again with `--ack <check>` for what they said yes to, or `--assign-me`. `--force`
says yes to every warning, never to an agent already on it.

## Move an issue through its states

<Diagram name="workspaces-issue-states" caption="The usual track; nothing enforces it" />

- Usual order: `backlog` → `todo` → `in_progress` → `in_review` → `done`.
- `cancelled` can be set from any state, and any state can be set from any other: the order is not enforced.
- `hive close` sets `done`, `hive close --reason` sets `cancelled`, and `hive reopen` sets `todo`.

Every change is a line in the issue's activity, signed by the person or agent who made it.

## Use your own statuses

A project can name its own steps, such as Code Review and QA. Each status sits in one of the six
states, and the board shows a column for each status in state order.

```bash
hive statuses edit                       # opens .hivemind/workflow.yaml; saved only once it is valid
hive statuses show                       # the statuses, each with its state
hive update MYP-3 --status "Code Review" # the state follows: in_review
hive list --status "Code Review"         # or --category in_review
```

- Every state needs at least one status, and ids must be unique: `hive statuses validate` names
  any problem.
- `--state` and `hive ctl set-state` still work, and pick the first status of that state.
- `board.columns` in the file groups several statuses into one column. Dropping a card there asks
  which status.
- With no `workflow.yaml` the statuses are the six states, as above.

## Split and link issues

```bash
hive task MYP-3 add "Write the test"     # MYP-3.1
hive new "…" --parent MYP-3
hive relate MYP-3 OPS-7 --type blocks    # written on both issues
hive move MYP-3 OPS                      # to another project; --copy keeps the original
```

Link types are `relates`, `blocks`, `blocked-by`, `duplicates`, `parent-of` and `child-of`. To use
ids from another project, run `hive workspace register` in both, then `hive workspace list`.

## What is in the folder

```text
.hivemind/
├── issues/MYP-1.md   one file per issue (sub-issues in issues/MYP-1/)
├── config.yaml       prefix and next id
├── workflow.yaml     your own statuses, when you made them
├── review.json       comments left on a diff
└── .agent.md         a summary of open issues for agents (not committed)
```

## If it didn't

| You see | Do |
|---|---|
| `no .hivemind/ found in this directory or any parent` | Run `hive init --prefix <PREFIX>` in the project folder first. |
| The prefix is refused | Use 2 to 10 capital letters or digits, starting with a letter. |
| The board does not show a new issue | Check it was filed in the same project folder. |
