# The phone app: native, real-time, in full control (2026-10-02)

Status: accepted (the person's direction, 2026-10-02). It amends design §9 of
[`multiplayer-2026-09-28.md`](multiplayer-2026-09-28.md) (M5): the phone was to see who needs the
person, answer, approve and watch. It now drives the person's agents as fully as their computer
does: it lists every agent, live; starts one, stops it, closes it; watches its terminal and types
into it; reads what it changed. It still runs no agents itself, and never sizes a terminal or
moves a keyboard between people.

The person's words, which decide what follows: *"I want to control them from phone"*, *"No we
dont use more of js framework they are slow"*, *"having lag free and realtime is must thing"*.

## 1. Stack (decided)

**Two native apps over one Rust core.** The core is `crates/hive-phone` (pairing, the person's
devices, the network, what needs the person, the agents, the terminal, push), with a UniFFI 0.32
facade in `crates/hive-phone-ffi` that generates Swift and Kotlin bindings.

- **iOS** (`apps/ios`): Swift, iOS 17+. UIKit draws the live terminal (a custom scroll view, one
  CoreText line per run); SwiftUI draws the lists, sheets and settings.
- **Android** (`apps/android`): Kotlin, Jetpack Compose, minSdk 29. The terminal is drawn on a
  Compose `Canvas`, line by line.

Why, from the research (appendix A):

| | Native ×2 + UniFFI (chosen) | Compose Multiplatform | Flutter | Rust UI toolkits |
|---|---|---|---|---|
| Scrolling, input | the platform's own, 120 Hz | Skia-drawn on iOS, 2–5× the RAM in one test | iOS touch input 80+ ms behind (open issue) | Slint on iOS drew in software until 2026-09-21; Makepad has no accessibility on phones |
| Rust | UniFFI, as Zeron, Element X, Proton, Bitwarden, Firefox | Gobley, pinned to UniFFI 0.29 | a second binding layer | native |
| The push extension (iOS) | Swift, linking Rust | Swift anyway | Swift anyway | hand-written glue |

Two UI codebases is the cost. It is kept small by keeping every decision in Rust (§3): the apps
draw what the core hands them and call it back, nothing more ("logic in packages, adapters in the
app", as for the desktop).

## 2. Layout

```
crates/hive-phone        the core: no FFI; `hive-phone` does in a terminal what the app does
crates/hive-phone-ffi    UniFFI facade: staticlib (iOS) + cdylib (Android, and the host for
                         generating bindings); `uniffi-bindgen` behind its `bindgen` feature
apps/android             Gradle (Kotlin DSL) project, applicationId com.hivemind.phone
apps/ios                 XcodeGen `project.yml` → Xcode project, bundle id com.hivemind.phone
scripts/phone/           build-android.sh, build-ios.sh: the core for each target + bindings
.github/workflows/       phone-android.yml (ubuntu), phone-ios.yml (macOS): on every push
                         touching the phone, any branch
```

No root Cargo workspace: each crate builds on its own (`--locked`), as hive-net and hive-phone do.
The facade's own profiles: `mobile` (release, no LTO: debug app builds) and `mobile-dist` (thin
LTO, one codegen unit, stripped: store builds). Generated Swift is committed and CI fails when it
drifts (`git diff --exit-code`); Kotlin is generated at build time.

## 3. Real-time, lag-free: the rules

1. **Nothing waits on the network to draw.** The app opens on what the core kept (what each device
   last said, `heard.json`); live data replaces it as it comes.
2. **One connection per device, kept while the app is in the foreground**, reused by everything
   (following, watching, calls). In the background (iOS suspends sockets) the core closes them; on
   the foreground it redials every device at once and ends every backoff wait. A failed dial backs
   off 250 ms → 16 s, reset after 30 s connected.
3. **Push, don't poll.** The device that runs the agents sends their list again whenever it
   changes (`spec/agents.md`, at most ten times a second); the phone never polls.
4. **Coalesce at every hop, keep only the newest.** The core folds a burst of changes into one
   immutable snapshot at most every 16 ms, tells the app its revision only (`changed(revision)`),
   and the app pulls the snapshot once on its main thread however many revisions came meanwhile.
5. **The terminal is parsed in Rust, drawn natively.** The core runs a VT emulator on the
   session's bytes on a thread of its own; per frame the app asks for the lines changed since the
   revision it last drew, in one call, their style runs packed as bytes (§5.3). Never a call per
   cell or per character: a UniFFI call costs microseconds, a frame at 120 Hz 8.3 ms.
6. **The terminal never reflows on the phone.** It is the session's size (its owner sizes it); the
   phone fits it to the width and zooms, so a resize never redraws on the phone's account.
7. **Answers land once.** Every action that could arrive twice (a notification action and the app,
   a retry) is idempotent on the device (`since`, the wait it names).
8. **Measured.** Debug builds count frame times and main-thread builds; a hitch gate (frames over
   their budget per second of scrolling) joins the UI tests.

## 4. Full control: what the phone may now do

`spec/agents.md` (0.1) holds the wire; in short, all as the person (the phone is their device,
`spec/pairing.md` 0.3), each recorded in the device's audit log as the phone:

| | How | Who answers |
|---|---|---|
| Every agent, live | the `agents` stream on the phone's connection to each device: `{t:"follow"}`, answered with the whole list now and again on each change | the app, `hive host` |
| What may be started | `agent.startable()`: the agents this device can start (id, label, their model and mode choices) and the workspace's frames (the folders to start them in, and the machine each is on) | the workspace's host |
| Start one | `agent.start({program, frame?, prompt?, model?, mode?})` → `{tile}`: as `hive ctl spawn`, in that frame | the workspace's host |
| Stop its turn | `agent.interrupt(tile)`: the keys its manifest says interrupt it (`interrupt`, Claude Code's: Esc) | the workspace's host |
| Close it | `agent.close(tile)`: ends its session and takes its tile off the board, as `hive ctl close` | the workspace's host |
| What it changed | `agent.diff(tile)`: the changes in the folder it runs in (its worktree's, else its frame's), files and a unified diff, cut at 512 KiB | the workspace's host |

Already there (M5): what needs the person (`needs`), answering it (`agent.answer`, Allow/Deny
with the agent's keys), sending a message (`agent.send`), watching a terminal and typing into it
(`terminal.open` attach-only, `terminal.write`), push.

The app asks the phone's own lock (Face ID, fingerprint or passcode) before it starts or closes an
agent: driving an agent is running code on the person's computer (design §10).

## 5. The core's facade (the contract both apps code against)

Names as Rust declares them; UniFFI gives Swift and Kotlin the camelCase forms (`type_text` →
`typeText`). `uniffi.toml`: `[bindings.kotlin] package_name = "com.hivemind.phone.core"`,
`cdylib_name = "hive_phone_ffi"`, `android = true` (amended 2026-10-02 from the Android build:
the error is flat, listeners are `Arc`, closing an agent is `close_agent`). Every `async fn` runs on one shared tokio runtime inside the core, so either
platform's executor can await it. Listeners are foreign traits (`#[uniffi::export(with_foreign)]`)
called from a core thread: the app hops to its main thread.

### 5.1 The phone

```rust
#[derive(uniffi::Object)] pub struct Phone;
impl Phone {
    #[uniffi::constructor] fn open(dir: String, name: String) -> Result<Arc<Phone>, PhoneError>;
        // dir: the app's private files; name: what the phone is called ("Priya's iPhone")
    fn id(&self) -> String;
    fn person(&self) -> Option<Person>;               // whose devices these are (name, colour)
    async fn pair(&self, link: String) -> Result<Paired, PhoneError>;   // the QR code's text
    async fn unpair(&self, device: String) -> Result<bool, PhoneError>; // false: not told; unpaired here all the same
    fn on_foreground(&self);                          // redial every device now (§3.2)
    fn on_background(&self);                          // close the connections
    fn follow(&self, listener: Arc<dyn OverviewListener>) -> Arc<Following>;
    fn overview(&self) -> Overview;                   // the newest snapshot (§5.2)
    async fn answer(&self, agent: AgentRef, since: u64, answer: Answer) -> Result<bool, PhoneError>;
        // false: it waits on that no more, or it was answered already
    async fn send(&self, agent: AgentRef, text: String) -> Result<bool, PhoneError>;  // false: no agent runs there
    async fn interrupt(&self, agent: AgentRef) -> Result<bool, PhoneError>;   // false: neither working nor waiting
    async fn close_agent(&self, agent: AgentRef) -> Result<bool, PhoneError>;   // not `close`: every object has one; false: closed already
    async fn startable(&self, device: String, workspace: String) -> Result<Startable, PhoneError>;
    async fn start(&self, device: String, workspace: String, start: Start) -> Result<AgentRef, PhoneError>;
    async fn diff(&self, agent: AgentRef) -> Result<Diff, PhoneError>;
    fn watch(&self, agent: AgentRef, listener: Arc<dyn ScreenListener>) -> Arc<Watch>;
    fn conversation(&self, agent: AgentRef, listener: Arc<dyn ConversationListener>) -> Arc<Conversation>;   // §5.4
    async fn push_to(&self, at: PushAt) -> Result<PushTold, PhoneError>;   // P6: each device given where
        // the app's push service tells the phone; call again as the app comes to the front
    async fn read_notice(&self, body: Vec<u8>) -> Result<Option<Notice>, PhoneError>;   // a push body,
        // decrypted; None: not to show (a device back it did not find away, a kind it does not know)
    async fn views(&self, device: String, workspace: String) -> Result<Vec<ViewInfo>, PhoneError>;   // §5.5
    async fn view_file(&self, device: String, workspace: String, view: String, path: String)
        -> Result<ViewFile, PhoneError>;
    fn open_view(&self, device: String, workspace: String, view: String, screen: Screen,
        listener: Arc<dyn ViewListener>) -> Arc<ViewSession>;
}
fn pairs_with(link: String) -> Option<PairsWith>;   // the device a scanned link pairs with, named before
                                                    // pairing runs; None: not a pairing link
#[derive(uniffi::Error, thiserror::Error)] #[uniffi(flat_error)] pub enum PhoneError {
    #[error("{0}")] NotPaired(String),    // nothing paired yet
    #[error("{0}")] Unreachable(String),  // no device holding it answered
    #[error("{0}")] Refused(String),      // the device said no (its message)
    #[error("{0}")] Invalid(String),      // not a link, text too long, …
    #[error("{0}")] Failed(String),       // anything else (disk, …)
}
// A flat error: Kotlin's `PhoneException.NotPaired(message)` (a field named `message` would clash
// with Throwable's), Swift's `PhoneError.NotPaired(message:)`; its text is the Display.
#[uniffi::export(with_foreign)] pub trait OverviewListener: Send + Sync { fn changed(&self, revision: u64); }
#[derive(uniffi::Object)] pub struct Following;   // fn stop(&self)
```

The core follows each device it reaches on its `agents` stream while the app is in the foreground
(`spec/agents.md` "Following"), and keeps each list as it comes, beside the workspaces the device
said it holds (`heard.json`), so the overview opens on them before any device says more (§3.1). A
device that sends no list within 10 s is asked `{t:"needs"}` instead (an app from before the
`agents` stream): of it, the overview shows the agents waiting on the person. `waiting` is a wait on
the person: an agent waiting on the agent supervising it (`approval`) is `Waiting` with no
`waiting`, and is not among `needs`. (Amended 2026-10-02: `Overview.workspaces`, and the agents'
order, which is `spec/agents.md`'s.) A device reached tells the workspaces it holds before what
waits there: until it has said that too (`answered_at`), nothing of it is in the overview, and the
apps say they are asking it rather than that nothing needs the person. (Amended 2026-10-02.)

### 5.3 The terminal

```rust
#[uniffi::export(with_foreign)] pub trait ScreenListener: Send + Sync {
    fn frame_ready(&self, revision: u64);          // at most one per 16 ms
    fn keyboard(&self, holder: Option<String>);    // who holds its keyboard; None: the person's devices
    fn ended(&self, code: Option<i64>);            // the session ended (its code); None: there is none to watch now
        // (it ended unseen, its workspace is not on that device now, or the device refused it). Once, last
}
#[derive(uniffi::Object)] pub struct Watch;
impl Watch {
    fn update(&self, since: u64) -> ScreenUpdate;  // what changed since the revision last drawn (0: all)
    fn type_text(&self, text: String);             // typed as it is, as the person
    fn type_keys(&self, keys: Vec<String>);        // tokens as `hive ctl keys` takes them: enter, escape, tab, up, …, ctrl-c
    fn stop(&self);
}
pub struct ScreenUpdate {
    revision: u64,
    cols: u16, rows: u16,                          // the session's size
    first_line: u64,                               // the oldest line kept (2,000 lines of scrollback)
    line_count: u64,                               // one past the newest line
    cursor_line: u64, cursor_col: u16, cursor_visible: bool,
    lines: Vec<ScreenLine>,                        // changed since `since`, oldest first; every line kept when `since` is 0 or older than the core remembers
}
pub struct ScreenLine { index: u64, text: String, runs: Vec<u8> }
```

A line's `index` is its number since the watch began, so it names the same line as it scrolls into
history. `runs` are 16 bytes each, little-endian: `start: u16`, `len: u16` (UTF-16 units of
`text`), `col: u16` (the column the run starts at), `flags: u16` (bit 0 bold, 1 dim, 2 italic,
3 underline, 4 inverse, 5 strikethrough, 6 hidden, 8 wide: a run of one double-width character),
`fg: u32`, `bg: u32` (top byte 0: the default colour; 1: palette index in the low byte; 2: RGB in the
low three bytes). A double-width character is always a run of its own, so the app places each run
at `col × cell width` and never measures text.

A watch goes on by itself across the background, the foreground and the device's reconnects, on
the connection kept to the device (§3.2): each connection is sent the screen whole first, which is
drawn in place of what was shown (from a reset, as the desktop redraws a session it attaches to
again), and what the person types while none takes it goes in on the next. A connection that goes
is no end: `ended` is the session's. (Amended 2026-10-02.)

### 5.4 The conversation

What an agent and the person say to each other (`spec/agents.md` "Conversation"), for a chat view
beside the terminal:

```rust
#[uniffi::export(with_foreign)] pub trait ConversationListener: Send + Sync {
    fn said(&self, entries: Vec<Entry>, anew: bool);   // oldest first, each once, at most one telling per 16 ms
        // anew: in place of all told before (or behind a divider): the first telling, and each after
        // the agent began another session (`/clear`); a resume within a session never is
    fn ended(&self, why: String);                      // told no more, and why: the device refused it, its
        // workspace is not on that device now, or the device is no longer the person's. Once, last
}
#[derive(uniffi::Object)] pub struct Conversation;    // fn stop(&self): nothing is told after
pub enum Who { Person, Agent, Tool }
pub struct Tool { id: String, name: String, about: Option<String> }   // the use's id; about: a file, a command, …
pub struct ToolResult { of: String, text: String, error: bool }       // of: the use it answers
pub struct Entry {
    id: String, at: u64, who: Who,
    text: Option<String>,        // the person's, or the agent's in markdown
    tool: Option<Tool>,          // a tool the agent used
    result: Option<ToolResult>,  // what a tool gave back
}
```

The core follows `agent.conversation` on the connection kept to the device, as a watch does, and
resumes from the last session and cursor it was told, so nothing is told twice; when the agent
begins another session, the device follows that one from its start (`spec/agents.md` 0.3), and the
app is told it anew. (Added 2026-10-02.)

### 5.5 Community views

The views a device offers the phone (§6.1), their files, and a view shown in the app's web view,
its host on the device (P8 step 3):

```rust
pub struct ViewInfo { id: String, name: String, version: String, page: String }   // page: the file to load
pub struct ViewFile { data: Vec<u8>, mime: String, csp: String }   // served as it is, under `csp`
pub enum ThemeMode { Dark, Light }
pub struct ViewFonts { ui: String, mono: String }
pub struct ViewTheme {
    mode: ThemeMode, colors: HashMap<String, String>,         // by token: bg, fg, …, each #rrggbb
    accent: Option<String>, radius: Option<u32>, fonts: Option<ViewFonts>, surface: Option<String>,
    terminal_background: Option<String>, glass: Option<bool>,
    status: HashMap<String, String>,                          // a colour per status tone
}
pub struct Screen { width: u32, height: u32, theme: ViewTheme }   // the web view's size, in CSS pixels
#[uniffi::export(with_foreign)] pub trait ViewListener: Send + Sync {
    fn said(&self, message: String);     // a view protocol message (JSON) for the page, as it is, in order
    fn ended(&self, why: ViewEnded);      // Restarting; else told once, last
}
pub enum ViewEnded { Restarting, Disabled { why: String }, Refused { why: String }, NotHeld, Unpaired }
#[derive(uniffi::Object)] pub struct ViewSession;
impl ViewSession {
    fn post(&self, message: String);      // what the page posted (JSON; anything else is dropped)
    fn screen(&self, screen: Screen);     // the phone turned, the keyboard came up, the look changed
    fn stop(&self);                       // nothing is told after; the device lets go of it
}
```

The app serves what `view_file` gives to the web view on the view's own origin, each file with its
`csp` as its `Content-Security-Policy`, loads `page`, posts what the page posts to `post`, and hands
the page what `said` says. The device serves the files as it serves its own windows: `__sdk.js`
(the view SDK), the page made for a view whose entry is a script, and every page with the SDK's
import map first (`spec/workspace-api.md` 0.14). A view goes on across the background, the
foreground and the device's reconnects, on the connection kept to the device (§3.2): a connection
that goes ends its session there, and on the next the core opens another, on the newest screen,
and tells `ended(Restarting)`: the app loads the page anew, so the view's handshake (`ready`, then
`hello`) is the new session's. What is posted from then until the page says it is ready is the page
of before's, and is dropped. A view the device's host turns off is `Disabled` (it flooded, or sent
what it may not); `Refused` is the device's no (it offers no such view now); `NotHeld` and
`Unpaired` as for a watch. (Added 2026-10-02.)

## 6. Screens (both apps)

1. **Pair.** First launch: *Pair with hivemind* → the camera reads the QR code on the computer
   (Settings → Devices → *Pair a phone*), or the link is pasted → "Pairing with desk…" → whose the
   phone is now, in their name and colour.
2. **Needs you** (home tab). What waits on the person, the longest first: agent, workspace ·
   machine, why (permission · question · plan), how long. A permission with `decide` has Allow and
   Deny on its row; a plan opens to Approve / Ask for changes; a question to a reply box. Empty:
   "Nothing needs you. 4 agents working." A device away: "desk is away · last heard 5 min ago",
   with what it last said.
3. **Agents** (tab). Every agent, by device and workspace: its state, its name, for how long.
   Swipe: Stop (when it can be interrupted and works), Close. **+** starts one (screen 6).
4. **Agent.** Its live terminal, fitted to the width, following the newest line until scrolled up;
   pinch to zoom. What it waits on, as a banner with its answers. A reply box (`send`) and *Type*,
   which types as the person with a row of keys (Esc, Tab, arrows, Enter, Ctrl-C). Stop, Diff,
   Close.
5. **Diff.** The files it changed with their counts; a file opens to its diff.
6. **Start.** Device → workspace → folder (frame) → agent (with its model and mode, when it has
   them) → prompt → Start (the phone's lock first) → the new agent's screen.
7. **Devices** (tab). Whose the phone is; each device, reachable or away; unpair; pair another.
8. **Notifications** (§8): Allow / Deny on a permission's notification, a tap opens the agent.
9. **Views** (tab, P8). The community views the person installed on their computer that say they
   work on a phone, each a tab of its own (§6.1).

### 6.1 Community views on the phone (added 2026-10-02)

The multiplayer design (§9 item 7, R12) had views that declare phone support as tabs on the phone,
in a web view speaking view protocol 1.5; this design left them out at first, reading "no JS
frameworks" as no web code on the phone at all. That holds for the app's own screens, which stay
native. A community view is web code wherever it runs (a sandboxed iframe on the computer), so on
the phone it runs in the platform's web view, the screens around it native:

- **One view, both screens.** A view lays itself out for a phone from `hello.device` (`{ touch:
  true, compact: true }`, protocol 1.5) and says it does with a manifest field (`"phone": true`);
  only those are offered on the phone. Authors write no second view.
- **Unchanged.** `@hivemind/view-sdk` takes its port from any window message of the handshake's
  shape (`client.ts` `connect`): a script the app adds at document start makes a `MessageChannel`,
  hands the view one end, and relays the other to the core.
- **The same sandbox.** The view's files come from the computer that has it installed (each
  checked against its hash), served as that computer serves them to its own windows, and are served
  to the web view on the view's own origin under the same CSP as on the desktop (`@hivemind/core/
  view-files` `pluginCsp`, which each file comes with: no network, no frames, scripts only from the
  package): `WKURLSchemeHandler` on iOS, `shouldInterceptRequest` on Android. No native API is
  exposed to it, only the view protocol.
- **The host stays on the computer.** `host-link.ts` (pure: no DOM, no React) moves out of the
  renderer into a package; the computer (the app's main process, or `hive host run`) runs it for
  the phone, its sources fed from what main holds, on a `view` stream of the phone's connection
  (the multiplayer design's `hive/view/1`, as one more named stream). The phone relays bytes; the
  permission checks, and the limits that turn off a view that floods or hogs, stay where they are.
- **Asked first.** A command from a view that starts or closes an agent asks the phone's lock, as
  the native screens do.
- **Its steps (P8).**
  1. *The host in a package.* `CommunityLink` (`host-link.ts`) and what it leans on (the commands it
     calls, the tile kinds a view may start, the status buckets) move into a package both the
     renderer and the computer's main process use; and `structure` is built by one pure function
     from what `listTiles` / `listFrames` (`workspace-doc`) and `link.list` give, which the
     renderer's view host uses too. No change a view can see; the views' e2e holds it.
  2. *A view for a remote screen.* The workspace API gains `view.list()` (the views installed here
     whose manifest says `phone`), `view.file(id, path)` (one of a view's files, checked against its
     package's hashes, at most 4 MiB), and `view.open(id, workspace)` → a session: what the view
     posts goes in as `view.post(session, message)`, what its host says comes back as the event
     `view.said [session, message]`, until `view.close(session)` or the connection goes. Main (and
     `hive host run`) runs a `CommunityLink` for each session, fed from what it holds, `hello` saying
     `device: { touch: true, compact: true }`. Its permissions are the manifest's and the caller's
     role's both; the phone's own (owner) by `phoneMay`. `hive-phone view` opens one and prints what
     its host says, for the e2e.
  3. *The core and the facade* (§5.5). `Phone::views(device, workspace)` (each view with the page
     to load), `Phone::view_file(…)` (its bytes, type and `csp`), and `Phone::open_view(…, screen,
     listener) → ViewSession` (`post(message)`, `screen(screen)`, `stop()`), on the connection
     kept to the device and opened again on the next, the view told to start again
     (`ViewEnded::Restarting`). The computer serves the files as its windows are served them
     (`__sdk.js`, `__entry.html` for a `.js` entry, the import map, each with its `csp`: one
     `serveViewFile` in `@hivemind/core/view-files`, the app's `hm-view:` handler's too), and shows
     the view on the phone's screen: its size and look in `hello`, then `resize` and `theme` as
     `view.screen` says they change (workspace API 0.14; `hive-phone view --size`).
  4. *The apps.* A web view per view tab: the bootstrap script that hands the SDK its port, the
     files served on the view's own origin under the `csp` each comes with, the messages relayed
     to the facade, the screen told as it changes, the page loaded anew on `Restarting`; a view
     that starts or closes an agent asks the phone's lock first. UI tests on CI.
  5. *Live terminals inside a view*, as below.
- **Later.** A live terminal inside a view (its `surfaceRects`, the hole the host fills) is the
  native terminal placed over the web view; until then a tile's surface opens the Agent screen.
- **The stores.** Apple's guideline 4.7 lets an app offer HTML5 and JavaScript plug-ins not in its
  binary, on conditions: no native API exposed to them (4.7.2), nothing shared with one without
  the person's consent each time (4.7.3), an index of what is offered (4.7.4), a way to report one
  (4.7.1). Google Play does not count JavaScript in a web view as downloaded code.

## 7. Testing

- **The core:** `cargo test` in `crates/hive-phone` (held to `conformance/`, as now) and in
  `crates/hive-phone-ffi` (the facade's own: the screen from known byte streams, coalescing, the
  packed runs).
- **The wire:** the desktop's e2e drives `hive-phone` against the real app, as it does for M5; each
  new call gets a case there.
- **Android:** JVM unit tests (the run decoder, view models over records built in the test) and
  Compose UI tests under Robolectric; the emulator with Maestro flows in CI (`ubuntu-latest` has
  KVM).
- **iOS:** XCTest and XCUITest on the simulator in CI (`macos` runners), with
  `CODE_SIGNING_ALLOWED=NO`: no Apple account needed to build or test.
- Every test passes `.claude/skills/test-audit/SKILL.md` and is shown to fail when what it guards
  is broken, as everywhere else.

## Appendix A: what the decision rests on

Researched 2026-10-02 by two agents, from the sources linked; unmarked figures are the source's own.

- **Zeron** (`zeronsh/zeron`, read at `80b946b1`): iOS UIKit over UniFFI 0.32 proc-macros
  (`crates/mobile`, `crate-type = ["lib","staticlib","cdylib"]`); a layout thread in Rust publishes
  immutable frames and calls `frame_ready(revision)`; Swift pulls only visible rows; change events
  coalesced to one per 16 ms. Simulator numbers (`docs/mobile-rewrite.md`): 30 ms to lay out 3,300
  rows, 0.19 ms per streamed token, 0 hitches in 671 idle and 536 streaming frames. The SwiftUI
  app it replaced re-rendered the whole session per token. On foreground it probes or redials
  every socket, ends all backoff waits and shows local state first; backoff 250 ms → 16 s. Android:
  draft PR #609, Compose over UniFFI/JNA, cargo-ndk for arm64-v8a and x86_64, 1.08% janky frames
  over a 600-turn transcript on an emulator.
- **UniFFI call cost:** Kotlin/JNA about 3.5–4 µs a call (uniffi-rs #3011, open); Swift 3.7 µs a
  record (#3013, open); plain JNI 115 ns. Hence one batched call per frame (§3.5).
- **Compose Multiplatform on iOS:** stable since 1.8 (May 2025); Software Mansion (July 2026) found
  157–251 MB RAM on iOS against 45–131 MB for UIKit views; JetBrains claims scrolling on par with
  SwiftUI. Gobley (its UniFFI binding) is pinned to UniFFI 0.29.5.
- **Flutter:** iOS touch input lags 80+ ms behind SwiftUI (flutter#170735, open; fixes unmerged).
- **Rust UI toolkits:** Slint drew in software on iOS until 1.18.1 (2026-09-21); Makepad's
  accessibility is a no-op on iOS and Android; GPUI's iOS backend is an open PR; Dioxus mobile
  renders in a WebView.
- **Terminal engines:** SwiftTerm on an iPhone 17e "never caught up" with sustained output (iOSSH
  #19); alacritty_terminal (Apache-2.0) is what Zed uses, not yet seen on phones (unverified there).
- **Others' phone control** (2026-10-02): Happy and Superset ship Expo apps; Remodex a Swift app;
  Synara the phone's browser; Orca an Expo companion. All offer start, stop, send and approve from
  the phone; none of the native ones draws a terminal.
- **Testing phones:** Maestro drives both platforms' accessibility trees; GitHub's `ubuntu-latest`
  runs the Android emulator with KVM, macOS runners the iOS simulator. This container has no KVM.
