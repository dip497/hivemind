# The last line: design plan

This is a static reading only. Every cost below is an estimate and none was measured. Paths are relative to `/home/user/hivemind`; `plugins/` means `/home/user/hivemind-plugins`.

**In one paragraph.** The pty daemon keeps choosing the screen line, with a better rule. Main gets a single owner, `TileLines` in `packages/host`, which combines "what the agent last said" with the screen line and serves it only to whoever watches that tile. The request text is not new data: it is `AgentItem.waiting`, which `AgentFeed` already computes once and every window already receives. The app draws the line and the request itself. Plugin views get a host-drawn strip and never the text.

## 1. Owner, computation, throttle and cost

**Screen line (stays with the daemon's `ScreenWatcher`).** The machine that runs a session derives its state (R6, `packages/agent-host/src/status-store.ts:15-18`).

What it does today:
- Each output chunk only adds the session to a dirty set (`pty-daemon.ts:397` → `screen-status.ts:67`).
- An unref'd tick runs every 1.2 s (`pty-daemon.ts:378`).
- The tick reads only the visible rows, in the screen worker (`screen-worker.ts:128-133, 152-159`).
- The line is the last row with text (`screen-status.ts:38-45`). It is told only when it changes (`:93-96`) and replayed to a viewer that connects (`pty-daemon.ts:692`).

What changes:
- **A1. Cursor-aware rule.** The worker's `rows` answer also gives each session's cursor row and whether the cursor is hidden (`screen-messages.ts:20`). It reads them through the same private `_core` access the worker already uses (`screen-worker.ts:29-46`). `lastLine` then walks up from the bottom and:
  - skips blank rows;
  - skips the cursor's row while the cursor shows (a prompt or an input box);
  - skips rows made only of box, block or braille glyphs;
  - skips rows the agent's manifest names as chrome, through a new optional `detect.chrome: LineTest[]` that uses the same non-backtracking tests (`detect-rules.ts:13-24`);
  - strips C0/C1 and bidi control characters, and cuts to 160 characters.
  - Today a shell at its prompt reports `$`, and a test asserts it (`tests/screen-status.test.ts:108-111`).
  - Older apps ignore the new manifest key, because `detect` validation only checks `rules`, `default` and `scope` (`manifest.ts:701-716`). `manifestVersion` stays 2.
- **A2. Clearing.** When a line that was told goes blank, the daemon tells `""` once. Today blank lines are skipped (`screen-status.ts:93`). When a session ends, nothing is told: main keeps the last line until the tile closes (`plane.ts:349-354`), which is the right line for an exited or asleep tile.
- **One `tile.line` event per tile stays.** Remote and device events are accepted only when `data.tileId` is a string naming one of their tiles (`remote/events.ts:2-5`, `device-sessions.ts:97-99`), so a batched event would be dropped.
- **No `DAEMON_PROTOCOL_VERSION` bump.** The shape is unchanged. An old main stores `""` (`plane.ts:381-383`) and Home skips it (`home.ts:115`).
  - The cost: a running protocol-1 daemon is kept across app upgrades (`daemon-client.ts:72`), so the new rule arrives only when that daemon restarts.
  - A bump would put every session to sleep and wake it (`daemon-client.ts:73-81`). That is too high a price for a display rule.

**Combined line (new owner `TileLines`, `packages/host/src/tile-lines.ts`).**
- Both adapters build it: the desktop's main (`apps/desktop/src/main/index.ts:1033-1037`) and `hive host` (`packages/host/src/headless.ts:394`).
- It replaces `control.lines` (`plane.ts:110`) and the rule that is written twice today (`index.ts:1617`, `headless.ts:509`).
- **Rule:** if the agent keeps a conversation (`keepsConversation`, `conversations.ts:28`), the line is what it last said. That is `""` until it says something (`conversations.ts:96-97`). Otherwise it is the screen line. This is spec/home.md:77-83. The same string comes back while nothing changes.
- **"Last said" becomes event-driven and asynchronous.** Today it costs one `statSync` per tile per Home refresh on Electron main (`conversations.ts:109`), re-resolves the transcript file every 5 s (`:85, 101`), and does a synchronous read of 64 KiB growing to 4 MiB (`conversation.ts:67-81`), measured at 14–72 ms per read (`docs/design/phone-browser-2026-10-03.md:1123-1124`). Instead:
  - Re-read only when that tile's own reports reach `plane.event`: `agent.event` (`plane.ts:401-413`) and `agent.reply` (`plane.ts:395-399`). Claude's PostToolUse sends `input.resolved` after every tool (`plugins/agents/claude/agent.yaml:396-397`).
  - Re-resolve the transcript file when the session id changes (`plane.ts:405-411`), not every 5 s.
  - Read only the bytes appended since the last offset; `readConversation` already takes a cursor (`conversation.ts:45-54`).
  - The first read of each tile is the existing widening read, made asynchronous and queued one at a time, so 50 agents are never parsed at once.
  - Only followed tiles are read, with at most one read in flight per tile.
- **Followers.**
  - Each connection has its own watch set. The owner keeps their union and drops a connection's set in the domain's `gone`.
  - Do not copy `terminal.watchActivity` here. It ignores which connection asked and is never cleared, so the last window to ask wins (`terminals.ts:206, 211-221`; `pty-activity.ts:42-48`).
  - Home counts as watching every tile while a phone follows it (`home.ts:150-155`).
  - Toasts and the CLI use a one-shot read that waits for any read already in flight.
- **Publishing.** The event `tile.lines {tileId: line}` goes through `publishTo` (`workspace-api/src/server.ts:87-90`), only to connections watching those tiles, with changed tiles only, at most once per 250 ms per connection.
- **Home.** A line change should refresh only the lines sequence. Today it rebuilds every layout row as well (`index.ts:1036` → `network.ts:627` → `home.ts:169`).

**Cost at 50 tiles (estimated, not measured)**

| Where | Per PTY chunk | Per tick or message |
|---|---|---|
| Daemon I/O thread and worker | No change: a `Set.add` | At most 50 dirty sessions of 40×120 per 1.2 s. The rows read already happens for status and today's line (`screen-status.ts:86-92`): about 2,000 row reads, about 240K cells, about 480 KB cloned. Added: two integers per session, and a scan of at most 40 rows per session on the I/O thread, the same order as `detect`. The 5,000 scrollback lines are never read (viewport only). Out: at most 50 `tile.line` frames per tick per viewer (at most 42/s), about 200 B each. |
| Electron main | None | Per `tile.line`: one Map compare and set, plus adding the tile to each watcher's pending set. Per connection: at most 4 messages/s, about 8 KB in the worst case (50 × 160 characters). "Last said": per tool use of a followed agent, one async stat, a read of the appended KiB and a parse of those lines; first reads run one at a time. Home, only while a phone follows: at most 4 lines-only refreshes/s (50 `Map.get` and 50 short `JSON.stringify`), with no layout rebuild. |
| Renderer (each window) | None | Per message: one `Map.set` per tile, and only that tile's row listeners run, so at most about 42 single-row renders/s. `modelTiles` is never rebuilt. With the panel hidden there is no work: rows unmount (`LayersPanel.tsx:568`), the watch empties, and main stops sending. |

- **When nothing follows:** no messages are sent and no transcripts are read.
- **A cost that stays:** the daemon still reads the viewport of a shell that printed, and for shells that read exists only for the line (`screen-status.ts:92-98`). It is bounded to sessions that printed. A per-tile watch sent to the daemon was rejected as more protocol surface than a viewport read is worth; revisit if measurement says otherwise.
- **Measure before and after** (built app, real GPU, uncapped, per CLAUDE.md):
  - the daemon's tick duration with 50 sessions printing;
  - main's event-loop delay at the 99th percentile while a phone follows;
  - Layers commits per second with 50 rows.

## 2. The request text for agents that need the person

- **Source:** `AgentItem.waiting` (`workspace-api/src/agents.ts:256-259`). `AgentFeed` builds it once for every reader (`agent-feed.ts:1-15, 103-120`) through `waitOn` (`needs.ts:52-68`):
  - A wait the hook holds comes first (`waits.ts:24-49`). Today that is Claude's PermissionRequest with `answer:` (`plugins/agents/claude/agent.yaml:378-391`).
  - Otherwise it falls back to the pending tool in the session file (`conversations.ts:67-78`).
- **Already in the window:** every window follows it (`Workspace.tsx:975-976`) but only uses `plan` (`:965-973`).
- **What it says** (one pure function, `lineFor(waiting, line)`, the same rule as the phone's `lineOf` in `crates/hive-web/www/app/home.ts:339-348`):
  - a tool: `Bash: <first line of about>`;
  - a question: `Asks: <question>`;
  - a plan: "Plan ready for review";
  - anything else: the kind word.
  - A supervised approval stays its lead's to answer (`useAgentAwareness.ts:73`).
- **Allow / Deny:**
  - Shown only when `waiting.decide` is set (`needs.ts:67`) on a permission.
  - They call `agentAnswer(tile, since, {decision})` (`hive-over-workspace.ts:118` → `answers.ts:135-145`). A late answer returns `answered:false`.
  - Shown only when `about` is a single line that is fully visible. Otherwise the row offers "Review", which shows the whole `about` first (up to 4,000 characters, `hive-agents/src/transcript.ts:26`).
- **Only Claude carries a tool or a question today.** Codex's PermissionRequest carries no tool (`plugins/agents/codex/agent.yaml:139-142`), so other agents show the kind word only. Capturing more is per-agent probing under the adding-an-agent-provider skill, not part of this design.
- **Never put the request or the line into SessionStatus or `agent.event`.** Both schemas are closed (`spec/status.schema.json:7`), and both are mirrored to every viewer and to push (`pty-daemon.ts:356, 764-766`).

## 3. The app's own surfaces, within DESIGN.md

**Layers row**
- Agent rows get a second line under the name:
  - 11px mono in pencil-text (`text-count font-mono`). Pencil-text is DESIGN's colour for secondary lines (`DESIGN.md:196`), and mono is for what a machine said (`:210`). Truncated, and lined up with the name.
  - Rows that need the person show the request instead, in Signal Amber. The One Voice Rule allows that (`:201`), and the phone already does it.
- The row grows to 44px. That needs a new spacing token and an amended Tile Row signature (`DESIGN.md:89, 298`).
- The line is drawn by a `<RowLine tileId>` that subscribes to its own tile, the way the tile header paints through refs (`TerminalTile.tsx:300-321`). It must not go through `modelTiles`, which rebuilds every row on every status event (`LayersPanel.tsx:370, 458-467`).
- A row that can be decided adds a band of compact 28px Deny / Allow buttons. DESIGN allows compact buttons in the panel (`:271`). Rows that need the person never hide their chip (`:236`).
- View menu: "Lines: All agents · Needs you · Off". This is a new key in `LayersPrefs`, parsed with a default (pattern at `settings-schema.ts:904`). Settings `v` stays 1, so no migration.
- I recommend "All agents" as the default, because that is what was asked. The text is pencil-coloured, still, with no colour or motion, so "quiet until it needs you" (`:168, 311`) holds. This default is the maintainer's call.
- Hover card (`LayersPanel.tsx:1197-1213`): shows the whole line, and for a wait the whole command with Allow / Deny. Today the card is `pointer-events-none` (`:1201`), so it must become a pinned popover when opened from "Review".

**In-app toast**
- A "needs" toast's detail is the request. The card already draws a detail line in 11px mono (`canvas-overlays.tsx:123-125`).
- Its actions are Allow / Deny, using the seam that is already reserved for them (`useAgentAwareness.ts:38-44`).
- There is a race: `status.changed` is published at once (`plane.ts:134`), while the wait arrives with the feed's refresh up to 250 ms later (`agent-feed.ts:62-68`). So the toast is pushed on the status change, as now, then updated when `agent.changed` brings the wait for that tile and `since`.
- `pushToast` must keep the toast's id for the same tile. Today it makes a new id (`:122-129`), which remounts the card.
- A "done" toast's detail is the tile's line, from the one-shot read.

**OS notification**
- Unchanged by default.
- Add an opt-in, off by default: Settings → Notifications → "Show commands and questions". When on, main writes the body from `agentFeed().waitingOf` (`agent-feed.ts:82-85`, wired at `index.ts:1037`) and from `TileLines`, waiting up to about 1 s for the feed's `waiting` event (`agent-feed.ts:154`).
- No buttons in OS notifications. Electron's notification actions are macOS-only, and the unsigned mac build may not show banners at all (`agent-notify.ts:59`).
- ntfy and web push never carry text (`pty-daemon.ts:504-505`, `host/src/push.ts:18-34`).

## 4. Plugin views

**No text crosses the MessagePort.** `ViewAgentStatus`, `NeedsInputReason` and `ViewEvent` keep their contract of no text an agent wrote (`hive-view-sdk/src/protocol.ts:151, 162, 193`; `docs/design/view-protocol-1.3-2026-09-23.md:17-19`; reaffirmed in `docs/design/customization-gaps-2026-10-22.md:99-102`). Three reasons:
- A view can pass what it holds out through exits that need no permission. `invokeResult` answers any agent that calls it (`view-host/src/link.ts:227-236`); Focus's `board` command already returns each row's `detail` to whoever calls (`plugins/views/focus/src/App.tsx:118`). The layout a view saves is shared by default (`hive-view-sdk/src/manifest.ts:62-64`).
- A first install of a sandboxed package arrives switched on, so the review sentence is the only consent (`hive-core/src/package-install.ts:95`).
- Redaction cannot be made reliable (`view-protocol-1.3:625-627`).

**What views get, drawn by the host:**
- **(a) Layers rail.** A view with `layers: true` already gets the app's Layers panel, and so the lines, with no change (`CommunityView.tsx:113-128`).
- **(b) Line slots, protocol 1.16.**
  - New feature `lineSlots` in `VIEW_FEATURES` (`protocol.ts:146`). `PROTOCOL_VERSION` stays 1.
  - New message `lineRects: {tileId, x, y, w, h}[]`, at most 64. Unknown tiles are refused and the rest taken, as for surfaces (`protocol.ts:803`).
  - The host draws the line in each rect. For a wait it draws the request and its own Allow / Deny, which call `agent.answer`. That is no more than a terminal surface already shows with no permission (`surface-slots.tsx:24-41`).
  - It is a separate message, not a field on `SurfaceRect`. An older host's parser drops unknown fields (`protocol.ts:647`) and would draw a full terminal. A view checks `supports("lineSlots")`, because an older host counts the unknown message against the view (`link.ts:306-310`).
  - Host rules: a rect may not be `inert`, it has a minimum height of 20px, and the buttons stay inside the host's box.
  - Desktop only. Phone and remote screens wire only `agentStatus` and widgets (`host/src/views.ts:355-361`), so they answer UNSUPPORTED.
  - The fake host in `@hivemind/view-sdk/testing` must refuse the same way (`protocol.ts:764`). It is not added to `CLIENT_CALLS`, because widgets place no surfaces (`client.ts:127-129`).
- **(c) Consent.** No permission is added: no `PERMISSION_WORDS` line, nothing new in the install review or on HiveHub.
- **Focus view.** Its `detail` stays category words (`plugins/views/focus/src/model.ts:41-43`). On a 1.16 host it places a line slot under each name. Its `board` command is unchanged.

**First-party only:** the line's text, the request's text, and Allow / Deny.

**If text in the sandbox is ever wanted:** it would need a `workspace:lines` permission, an install that arrives switched off, and the `invokeResult` and shared-layout exits closed for that view first. I would not do it.

## 5. Phone and peers

- **Phone page.** Home already keeps lines as a separate sequence (`spec/home.md:47-48`) under this rule (`:77-83`), and the page already puts the wait before the line (`hive-web/www/app/home.ts:339-348`). The better screen rule reaches it for free. After step 3 its lines come from `TileLines`: no `statSync` per refresh and no layout rebuild per line. Push stays text-free. I found no Home-lines renderer in the Android app (grep).
- **Guests.**
  - Guests with "Can view" already watch terminals live (`workspace-api/src/roles.ts:43-49`), so lines expose nothing new.
  - But `tile.lines` must be filtered per peer by `peer.holds`, as `terminal.activity` is (`peers.ts:211-214`), and `tile.watchLines` must be checked the same way (`:294`). An event with no rule goes to every peer unfiltered (`:215-217`).
  - Add the filter in slice 1. Serve guest windows later.
- **Other devices and ssh hosts.** Their daemons' `tile.line` events reach `TileLines` through the existing filters. A plain `ssh -tt` remote keeps no screen, so it has no line (`remote/pty.ts:1-5`).

## 6. First thin slice and its tests

**Slice 1:** a terminal's last line and a waiting agent's request in the Layers row. Desktop windows, local and remote daemons. No change to "last said" and no change to Home. Agents that keep a conversation show their request while waiting and their state otherwise.

What it builds:
1. **agent-host:** the cursor in the `rows` answer, the new `lastLine` rule (without manifest chrome), and `""` when a line goes blank.
2. **host:** `TileLines` holding screen lines, per-connection watch sets, `publishTo`, a 250 ms flush, and `plane` passing `(bare, line)`.
3. **workspace-api:** the method `tile.watchLines` (role `view`, like `roles.ts:48`) and the event `tile.lines`, each defined once in `methods.ts`, plus the peer filter.
4. **renderer:**
   - `line-store.ts`, which unions the window's watches like `ActivityStore` (`view-services.ts:51-66`) and keeps per-tile listeners like `agent-status-bus.ts:112-124`;
   - a store of each tile's wait from the agent feed, giving back the same object while `since`, tool, about and asks stay the same;
   - `lineFor`, `RowLine`, and the View menu preference;
   - the DESIGN.md amendment.
5. **Docs:** `guide/(use)/know-who-is-waiting.mdx` and a CHANGELOG line.

Tests. Each must pass the test-audit gate and be shown failing with `scripts/mutate.sh`:
- **agent-host:** `tests/screen-status.test.ts`, driven through a `SessionManager` with a fake pty and the real worker (as `tests/screen-replay.test.ts:7-25`).
  - Output `npm test\r\n214 tests passed\r\n$ ` → told `214 tests passed`.
  - Clearing the screen → `""` told once.
  - No new output → nothing told.
  - This replaces the `$` contract at `:108-111`; the commit says why.
  - Mutations: remove the cursor skip (reports `$` again); remove the blank tell.
- **host:** `tests/tile-lines.test.ts`, at the `WorkspaceServer` boundary with two connections.
  - A line reaches only its watcher, and a repeat tells nobody.
  - After `gone`, nothing is sent.
  - A new watch replays the tile's current line.
  - Mutation: use `publish` instead of `publishTo`.
- **workspace-api, peers:** a `tile.lines` for a tile outside the peer's workspace never reaches it. Mutation: remove the filter.
- **renderer:** a table test for `lineFor` covering tool with the first line of about, question, plan, kind only, line, nothing, and bidi characters stripped.
- **One e2e:** a shell prints `214 tests passed` and the Layers row shows it. Hiding and showing the panel shows it again with no new output.
- **Performance:** the numbers from §1, before and after, in the commit.

## 7. Risks, and what I would not do

**Risks**
- The new rule only arrives once a reused protocol-1 daemon restarts.
- Agents without `detect.chrome` may show a footer or a timer line until their manifest gets one. That line can change on every tick: at most 0.83 events/s per tile.
- The line is untrusted. Any process in a tile can set its tile's line over the control-plane socket (`plane.ts:468-474`; asserted in `tests/plane-status.test.ts:106-111`). Render it as text only, with backticks set as code; never as markdown or HTML.
- Commands shown on screen may contain secrets. That is why the OS-notification text is opt-in.
- Allowing from a row is one click. The guards are: the whole single line is visible, otherwise "Review"; focus never rests on Allow; `since` is checked again on answer.
- The notification race between the status change and the wait (§3).
- A cold "last said" read can take 14–72 ms of parsing on main per agent. It is asynchronous and one at a time, but still unmeasured.

**What I would not do**
- Put the line or the request in SessionStatus, `AgentItem` or `agent.changed`. It would break the closed schemas, reach push, and make `AgentFeed` rebuild every agent on each line (`agent-feed.ts:103-120`).
- Read lines from the renderer's xterm. Tiles hidden for more than 1 s stop receiving bytes (`TerminalTile.tsx:606-619`), unmounted tiles have none, and N windows would mean N readers.
- Run a second headless xterm in main, or take the tail of `OutputRecorder`. The recorder is not cursor-aware and records only what someone shows (`terminals.ts:468-472`).
- Raise `DAEMON_PROTOCOL_VERSION`.
- Batch several tiles into one daemon event.
- Route the line through `modelTiles`, through LayersPanel state, or through `names`/`structure`. A title change already resends the whole structure to views (`plugin-link.tsx:237-253`).
- Give views text or an answer verb.
- Put text in ntfy or web push.
