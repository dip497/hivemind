# Connect: one offer, decided when someone uses it (2026-10-13)

Status: proposed, waiting for the maintainer's go. Branch `feat/browser-app`. Replaces the People
page rework and the Another-computer split (6f38b64); the QR component (bbe81cd) stays.

**Verdict.** One button makes one offer (QR, six words, link). Whoever uses it only *asks*: the
offer carries no authority. This computer then asks once: **It's me**, **Someone else** with a
role, or **Deny**. "It's me" gives the person key, so it needs words that are new for each request
and shown on both screens, and a yes on both screens. The offer's own six words cannot serve: anyone
holding the link has them. This is stricter than today, where whoever proves the code first gets
the person key and nobody is asked.

## 1. Problem

**Goal.** One way to connect anything to this computer (your phone, your other computer, a
friend), and one list of what is connected.

**Constraints.** A leaked link can do nothing before approval. Full access (the person key) is
never one careless click away. "Someone else" stays role-limited to the workspace the offer was
made from. Deny and expiry leave nothing behind. No compatibility with older apps (everyone
updates).

**Known problem.** Device enrolment plus guest admission behind one request queue: the
"pending request + human approval" shape of Tailscale device approval and Figma access requests,
with a short authentication string (SAS) for the full-trust branch.

## 3. Prior art

- **Signal, link a device.** The new device's QR carries its key; the primary scans it. No words
  are compared. The attack seen in the wild is the owner scanning an attacker's QR disguised as an
  invite (cloud.google.com/blog/topics/threat-intelligence/russia-targeting-signal-messenger).
  Lesson: the full-trust branch fails through the owner's own click, so that click must check
  something the attacker cannot copy.
- **Magic Wormhole.** SPAKE2 turns a short code into a key; one guess per code; `--verify` adds a
  string to compare (magic-wormhole.readthedocs.io/en/latest/welcome.html). Lesson: the code
  proves a shared secret, not who is holding it.
- **Bluetooth numeric comparison.** Six digits on both screens, a yes on both; it defeats a MITM
  that Just Works does not (NIST SP 800-121r2). Lesson: confirm on both sides.
- **ZRTP SAS (RFC 6189).** 16–20 bits are enough when the attacker gets one try at a match.
- **Tailscale device approval.** A new node cannot send traffic until an admin approves it
  (tailscale.com/docs/features/access-control/device-management/device-approval). Lesson: the
  pending state grants nothing.
- **Figma / Notion.** The inviter picks the role; access requests are approved per person. Notion's
  workspace "secret link" admits anyone automatically (notion.com/help/add-members-admins-guests-and-groups):
  that is the leaked-link escalation to avoid.
- **Choosing at approval time is new.** None of Quick Share, AirDrop or Matter commissioning picks
  "my device or someone else" at approval: each decides it before the exchange. So the safeguards
  below are ours to get right, not copied.

## 4. Options

```
A. One offer, the use decided at approval      B. One page, two offers           C. One offer, the joiner says
   (chosen)                                       ("For me" / "For someone")        "I'm the owner's device"
 offer ──use──▶ request ──▶ [It's me|Someone|Deny]   button ─▶ question ─▶ pair code      offer ─▶ joiner claims ─▶ check
```

| | A: decided at approval | B: two offers behind one page | C: the joiner chooses |
|---|---|---|---|
| Steps for the person | 1 button, 1 decision at the prompt | 1 button + "who is it for" | 1 button; the joiner picks |
| Leaked link, before approval | a request on screen; nothing granted | pair code: **the person key**, as today | joiner claims "me": prompt with words |
| Full-trust check | per-request words on both screens, yes on both | none today; could add the same words | the same words |
| Where it breaks | the person clicks It's me on a stranger's request; mismatching words are the stop | the person-key race stays, unless B adds the prompt too, and then it is A with an extra question | the joiner picks the branch, so a leaked link aims at the strongest one first |

Limits, in numbers:

- **Guessing the offer.** 48 bits, 3 wrong proofs and it is void: 3 / 2^48 ≈ 1e-14 per offer, at
  any number of offers.
- **Guessing the words.** 24 bits (3 words from 256), one try per request. The attacker cannot
  grind keys towards a match, because the words mix in a nonce the offering computer sends privately
  to each requester (§5.3), so the target is unknown. Each request costs the attacker a prompt the
  person must answer, and requests are capped at 3 waiting at once (§5.5): 2^-24 per request.
- **The mDNS tag.** It is 32 bits of SHA-256 of the code. A LAN watcher can search the 2^48 codes
  offline: about 2.8e14 hashes, roughly 8 h at 1e10/s. That is longer than a 5-minute code, not a
  24-hour one. With approval required, finding the code buys only a request. It stays a written
  ceiling (§6).

**Choice: A.** B keeps today's silent person-key race unless it grows the prompt, and then it is A
plus a question the maintainer asked to drop. C lets the requester aim a leaked link at the
strongest branch. A keeps the decision with the person who has the most context, at the moment
they see who is asking.

## 5. Design

### 5.1 The offer

`net:connect-offer` in main makes one offer per window: a 48-bit code (today's six words), the
workspace of the window it was made in (or none, from Home), expiry 24 h, single use. It contains
the voucher as today's links do. Link: `hivemind://connect/<device>#<json>` with device, addrs,
relay, code, name and voucher. It carries neither a workspace id nor a role: those stay on this
computer, as the invite's role does today. A new offer voids the last one. Cancel voids it.

### 5.2 The request (`hive/pair/1`, hello `connect`)

The joiner sends `{connect: 1, proof: HMAC(code, "hive/connect/1 entering\n" ‖ offerer ‖ joiner), kind, name, certificate?, nonce_j}`.
A phone sends no certificate. The offering side checks the proof as today. A wrong proof counts
toward the 3 tries. It then:

1. picks a fresh 16-byte `nonce_o` for this request;
2. computes `words = 3 words of HMAC(code, "hive/connect/1 sas\n" ‖ offerer ‖ joiner ‖ nonce_o ‖ nonce_j)`;
3. answers `{pending: true, proof_o, nonce_o}` on the same stream;
4. raises the prompt.

The joiner checks `proof_o`, computes the same words, and shows "Connecting to Asha's computer.
Words: maple · river · lamp". It then waits on a second stream, `{connect: 1, wait: id}`, held up to
170 s, as join requests are today.

### 5.3 The prompt: one queue, two answer paths

The prompt reads: "iPhone wants to connect · maple · river · lamp", with buttons
**It's me (the words match)** · **Someone else: [Can view ▾]** · **Deny**.

- **The queue.** Join requests from `hive/join` links, pairing requests and connect requests show
  in one prompt component in the renderer, keyed by request id, with Deny focused by default.
  `people.asked` keeps feeding it.
- **It's me.** Main runs today's pairing `answer()`: a phone gets a certificate; an app or host gets
  the person key. The joiner's screen asks first: "Asha's computer says this is Asha's. Words match?
  **Yes, make this computer Asha's** · No". The key is sent only after that yes. This protects an
  honest friend's computer from becoming Asha's through Asha's mistake. "It's me" is not offered
  when the requester is a host, because a host has its own direction (§5.6).
- **Someone else.** Shown only when the offer has a workspace and the requester has a certificate,
  so not for a phone. Main calls a new owner-only host method, `people.admit(workspace, certificate,
  profile, role)`: today's Allow path (grant, remember, addDevice, admittedChanged) without an
  invite record. The role is the one picked in the prompt, from view / edit / terminals, never
  agents.
- **Deny, a timeout, or the offer expiring.** The joiner gets `declined` or `expired`. Nothing is
  written. The offer stays open for the next request until it expires, so a stranger cannot burn
  it before the real device arrives.
- **Either Allow.** The offer is spent. Any other waiting requests for it get `expired`.

### 5.4 Connect page

- **Settings → Connect** (group Connect: Connect, API access):
  1. Connect, the button, then the offer: QR, words, Copy link, the time left, Cancel.
  2. Have a code? Join, a small link that opens the join form, which now takes connect, join, pair
     and host links, and six words.
  3. Connected: one list. Your devices show their kind and Unpair. People show their role
     (select) and Remove, for the workspace in this window.
- **Old page ids.** `share`, `people`, `devices` and `your-devices` resolve to `connect`.
- **Advanced → In a browser.** "Open in a browser on this computer" and its More options get their
  own page in Advanced.
- **First screen.** Home with no workspace gets "Have a code? Join".

### 5.5 What a leaked link can do

| When | With the link alone |
|---|---|
| Before use | redeem the voucher, so it gets onto a closed network's relays until expiry (as today); send requests: each is a prompt; at most 3 wait at once, and a fourth gets `busy` |
| At the prompt | nothing, unless the person clicks; It's me needs words matching on a screen the person holds |
| After either Allow | `expired` |
| Replay | the proof binds both device ids (TLS); `nonce_o` is per request; the offer is single use |

### 5.6 Kept apart, on purpose

- **A host offers its own code** (`hive host pair`). The app enters it under Have a code? Join, and
  gives the host its key (today's `give`, with today's "this host becomes you" line). This is the
  other direction, so it is not folded into the offer.
- **Reusable links for many guests** (`hive share --uses`) stay a CLI and API feature. The page
  makes single-use offers.
- **The `invite` rule** (admit without asking) is kept, for `hive/join` links only. A connect offer
  always asks.

## 6. Pre-mortem (a year on, it failed)

1. **"I clicked It's me on my friend's request."** The words on the friend's screen matched what
   they read out. Fix: the joiner side asks too (§5.3), and the prompt names the requester's kind and
   network address, "a computer, via relay", before the buttons. Unpair stays one click, with this
   ceiling: **Unpair does not rotate the person key** (as today). Rotating it is the upgrade path,
   written down, not built here.
2. **Phones broke.** The phone page, iOS and Android speak `pair`, not `connect`. Fix: the phone
   side changes in the same series, in `crates/hive-phone`, which the page and the apps share. iOS
   `PairView.swift` was not read (§8). Its build is a gate in §7.
3. **Waiting requests pile up** from a leaked 24 h link. Fix: at most 3 waiting, the rest `busy`,
   and 3 wrong proofs void the offer. Ceiling: a LAN watcher can recover the code from the mDNS tag
   in hours (§4), which buys only prompts.

## 7. Build order (each a commit, tests failing first, mutation-checked)

1. **Protocol.** `spec/pairing.md` 0.9 `connect`: request, pending, wait, words. Conformance cases
   for the words and proofs. Unit tests in `packages/workspace-host` (words equal on both sides;
   change either nonce and they differ; a wrong proof counts a try).
2. **Main.** The connect offer and the request queue, with It's me only after the joiner's yes,
   reusing `answer()`. `people.admit` on the host. Units: Deny and expiry write nothing; either
   Allow spends the offer; a fourth waiting request gets `busy`.
3. **Joiner side.** Desktop `pairEnter` and the join form. `crates/hive-phone` and the phone page
   show the words and wait.
4. **Prompt.** One request toast for join, pair and connect. e2e: a phone connects (It's me after
   the words); a second app connects as Someone else with Can view and cannot write; Deny leaves
   nothing; the offer expired.
5. **Page.** Connect, Connected list, Have a code? Join, Advanced → In a browser, old ids. e2e:
   settings-layout and the specs that pair or invite (phone-pairing, host-pairing,
   multiplayer-join, multiplayer-people, your-devices), one run at a time. Before and after
   screenshots.
