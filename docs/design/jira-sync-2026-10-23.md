## 1. Goal

A hivemind workspace linked to Jira works the same Jira the team already uses:

- **Every status, in every workflow, is mirrored.** This covers company-managed and team-managed
  projects, Scrum, Kanban and simple boards, and a different workflow per issue type, on **Jira
  Cloud**. (Data Center is deferred, §9.0; the transport interface keeps room for it.) The hive board shows Jira's own columns and statuses, plus the hive-only statuses
  the team adds (e.g. **PR Created**). Both exist side by side.
- **By default it pulls issues assigned to me.** A switch pulls everything, and the person can
  browse the rest. Starting work on an issue that is unassigned, or assigned to someone else,
  asks first.
- **Agents work issues on their own branches.** Finishing opens a GitHub PR, the issue moves to
  PR Created, and merging moves it to Done. Every move goes back to Jira as a legal transition.
- **Real two-way background sync, no LLM in the loop.** The plugin's service talks to Jira
  itself: over the Atlassian Rovo MCP server after "Sign in with Atlassian" (the default), or over
  REST with a scoped API token. Both are one `JiraTransport`, and both write through the same
  deterministic `hive ingest` path. A `jira` agent skill with preset prompts (import an epic,
  triage a sprint, start or complete an issue) sits on top of the service and writes only through
  ingest.

```
Jira (any workflow) ──discover──▶ hive workflow (Jira statuses + hive-only statuses)
        │                                   │
        └──pull (mine | all | jql)──▶ mirrored issues ──start (assignment guard)──▶ branch + worktree + agent
                                            │                                                  │
                            Jira transition ◀── every status change ◀── PR created ◀── agent completes
                                                                         │
                                                         PR merged ──▶ Done ──▶ Jira transition
```

### Non-goals (for now)

- Editing Jira workflows from hive. Hive adapts to the workflow and never changes it.
- Jira Service Management queues and SLAs, worklogs/time tracking, attachments (we link them,
  we don't download them), Confluence.
- Webhook delivery to the desktop (there's no public URL; see §9.4).

## 2. Principles

1. **Learn the workflow from Jira; never hardcode it.** Statuses, categories, transitions, board
   columns and custom fields are read from Jira and cached. Whatever Jira returns that we didn't
   expect gets a sensible default and a visible note, never a crash.
2. **Jira owns its fields; hive owns its own.** A field has exactly one owner, and the one field
   both sides write (status) follows a written conflict rule.
3. **Sync is deterministic and idempotent.** Re-running any sync changes nothing. A sync killed
   halfway and restarted produces no duplicates and loses nothing.
4. **Nothing is lost.** Hive never deletes a mirrored issue because Jira stopped returning it. It
   archives the issue and says why.
5. **No surprises for the person.** Hive warns before acting on someone else's or nobody's issue.
   It never pushes to Jira without the opt-in. Every write it makes to Jira shows up in the
   issue's activity.
6. **Core stays tracker-neutral.** Jira is a plugin. Linear, GitHub Issues and others reuse the
   same core contract.

## 3. Architecture

| **Core** (ships with hivemind; tracker-neutral) | **Jira plugin** `@dip497/jira` (HiveHub tool package) |
|---|---|
| Per-workspace **workflow** (dynamic statuses with categories), §4 | Discovering the Jira workflow, board and fields, §6 |
| `external` link, mirrored-issue storage, keys as ids, §5 | Pull scopes, JQL building, incremental polling, §7 |
| **`hive ingest`**: deterministic upsert that every source writes through, §5.4 | Push queue: transitions, comments, assignee, remote links, §8 |
| **Start-work guard** (assignment and readiness checks), §10 | Transports: Rovo MCP (default, OAuth sign-in) / REST with a scoped API token, §9 |
| Issue → branch → worktree → PR lifecycle, PR watcher, §11 | ADF ↔ markdown, §6.5 |
| `issue.changed` events; issue writes for services; `secret` settings, §12 | Sync tile (status, mapping, conflicts, browse), §13 |

The plugin runs as a tool-package **service**: a long-lived Node child of the host, with its own
drive grant, restart backoff and a log file (`packages/host/src/services.ts`). Next to it sits a
**tile** for the UI. Both exist on main today. §12 lists what core has to add.

## 4. Core: a workflow per workspace

### 4.1 Model

The six fixed states become **categories**. A workspace defines **statuses**, and each status
belongs to one category:

| Category (stable contract) | Jira `statusCategory` default | Meaning to hive |
|---|---|---|
| `backlog` | `new` and not on the board / in backlog | not planned |
| `todo` | `new` | planned, not started |
| `in_progress` | `indeterminate` | someone is on it |
| `in_review` | `indeterminate` whose name looks like review/QA/test (a heuristic the person can edit) | work finished, being checked |
| `done` | `done` | finished |
| `cancelled` | `done` with a resolution in the "cancelled" list (Won't Do, Duplicate, Cannot Reproduce…) | dropped |

An issue gets a new `status` field (the status id) and keeps `state`, which is now always that
status's category. That makes the change **backward compatible**:

- The view protocol (`ISSUE_STATES`, `hive-view-sdk/src/protocol.ts:262`, `PROTOCOL_VERSION = 1`),
  the widget API, `agent-context.ts`, templates, filters and every existing view keep working on
  `state`.
- `hive ctl set-state X in_progress` still works. It picks the status the workflow marks as that
  category's default (for a Jira-linked issue, the one reachable by a legal transition, §8.2).
- New surfaces read `status` (board columns, the status picker, CLI `--status`).
- A workspace with no `workflow.yaml` gets the six built-in statuses (`status == state`). That's
  how every workspace works today, unchanged.

### 4.2 `.hivemind/workflow.yaml`

```yaml
version: 1
statuses:                         # every status any issue in this workspace may have
  - id: jira:10000                # source-scoped id; never the name (names change, ids don't)
    name: To Do
    category: todo
    color: "#8590a2"              # from Jira's category colour unless overridden
    source: jira
  - id: jira:10001
    name: In Progress
    category: in_progress
    source: jira
  - id: jira:10005
    name: Code Review
    category: in_review
    source: jira
  - id: hive:pr-created           # hive-only status: exists only in hive
    name: PR Created
    category: in_review
    source: hive
    jira: { follow: jira:10005 }  # what Jira shows while an issue sits here (or `stay`); default: the
                                  # review-category status reachable by a legal transition (decided 2026-10-24)
  - id: jira:10002
    name: Done
    category: done
    source: jira
issueTypes:                       # per-type workflows (Jira allows one per issue type)
  "jira:10004":                   # Bug
    statuses: [jira:10000, jira:10001, jira:10005, hive:pr-created, jira:10002]
    initial: jira:10000
    transitions:                  # learned; see 6.3
      - { id: "21", from: [jira:10000], to: jira:10001, name: Start, screen: false }
      - { id: "31", from: "*",         to: jira:10002, name: Done,  screen: true, fields: [resolution] }
board:                            # Jira board columns, each mapping several statuses
  id: 12
  type: scrum
  columns:
    - { name: "To Do",       statuses: [jira:10000] }
    - { name: "In Progress", statuses: [jira:10001] }
    - { name: "Review",      statuses: [jira:10005, hive:pr-created] }
    - { name: "Done",        statuses: [jira:10002] }
local:                            # hive's rules for hive-only statuses
  onPrOpened: hive:pr-created
  onPrMerged: category:done       # = the done-category status reachable by a legal transition
  onPrClosed: category:in_progress
```

- **Owner.** The Jira plugin writes the `jira:*` statuses and `board`. The person (or the tile's
  editor) owns `hive:*` statuses, `local` and display overrides. Re-discovery never removes a
  status that any issue still uses; it marks it `retired: true`.
- **Several sources.** A workspace can link more than one Jira project or board (a monorepo).
  *P-R correction:* Jira status ids are **site-wide**. Since 2026-10-12, team-managed workflows can
  use global statuses (CHANGE-3498/3410), so one status id legitimately appears in several
  projects, team-managed and company-managed alike.
  - Prefixing ids per project (`jira:PAY:10001`) would split one status into several, so ids are
    scoped by **site** only: `jira:10001` for one site, `jira:<site>:10001` when two sites are
    linked.
  - Which statuses a project and issue type can use is recorded in `issueTypes`, keyed
    `"<projectId>/<issueTypeId>"` when more than one project is linked.
- **Validation.** Each status has exactly one category. Each category has at least one status.
  The ids are unique.

## 5. Core: linking issues to an external tracker and storing them

### 5.1 Frontmatter

```yaml
---
id: PAY-318                    # the Jira key IS the hive id for mirrored issues (5.2)
title: Retry failed webhooks
state: in_review               # category (always derived from status)
status: hive:pr-created
external:
  provider: jira
  source: jira:acme/PAY        # which link (site + project) owns it
  id: "10423"                  # Jira's numeric id: stable across key changes
  key: PAY-318
  url: https://acme.atlassian.net/browse/PAY-318
  type: { id: "10004", name: Bug, hierarchyLevel: 0 }
  remoteStatus: jira:10005     # Jira's status right now (may differ from `status` while in a hive-only status)
  assignee: { accountId: 5b10…, name: Ujjwal Solanki, me: true }
  reporter: { accountId: …, name: … }
  sprint: { id: 87, name: "Sprint 42", state: active }
  priority: High
  estimate: 3
  parentKey: PAY-300           # epic / parent
  remoteUpdated: 2026-10-22T09:14:00.000Z
  syncedAt: 2026-10-24T08:00:12Z
  archived: null               # or { reason: "left scope" | "deleted" | "no access", at }
branch: PAY-318-retry-failed-webhooks
pr: { repo: acme/payments, number: 1187, url: https://github.com/acme/payments/pull/1187, state: open }
github: 1187                   # kept for old readers; mirrors pr.number
assignee: { type: agent, id: claude }   # hive's assignee (who works it here) — NOT Jira's
---
```

Core fixes needed for this to survive (*verified on origin/main, 2026-10-24*):

- **Keep unknown keys.** `IssueFrontmatterZ` (`packages/hive-core/src/types.ts:55`) strips them,
  and `serializeIssue` (`storage.ts:339-357`) writes only its 10 known keys. Make the schema
  `.loose()` (zod 4's name for `.passthrough()`; the catalog pins zod 4.6.5). Write the known keys
  in their order, then the unknown ones.
- **Same for the config.** `ConfigZ` (`types.ts:154`) strips unknown keys. It is rewritten by:
  - `allocateId` (`storage.ts:195-204`), for top-level issues only;
  - `writeConfig` (`:176`);
  - the self-heal in `readConfig` (`:121-133`), which rebuilds from known keys;
  - `migrateWorkspace` (`:263`);
  - `hive agent detect` (`apps/cli/src/commands/agent.ts:67`);
  - both init paths.

  All of them must keep unknown keys.
- **Keep everything in the body.** `parseSections` (`storage.ts:475-526`) never fills `extra`,
  but `serializeSections` writes it after Activity, so it is lost on the next save. Lost today:
  - every Acceptance-criteria line that isn't `- [ ]` / `- [x]`;
  - every Activity line that doesn't match `ACT_RE`;
  - any unknown heading after those sections.

  `ACT_RE` takes `who` as `\S+` and one line per row, and `appendActivity` writes multi-line
  comments that the next read cuts to the first line. Add an optional
  `<!-- id:jira-c-10023 -->` row marker and an `ActivityEntry.id`, so comments are matched, not
  duplicated.
- **Don't split Jira descriptions.** `SEC_AC_LINE` (`storage.ts:471`) treats a plain
  "Acceptance criteria" line *anywhere* in the body as the AC heading. Jira descriptions often
  contain exactly that line (fixture `OPS-1`). Match only the real `## Acceptance criteria`
  heading.
- **Two gray-matter traps** (both verified):
  - Unquoted ISO timestamps parse as `Date`. `IsoZ` then rejects them, and `listIssues`
    silently skips the file (`storage.ts:402`). Nested `external.*` timestamps need coercion, or
    quoting on write.
  - `matter(raw)` caches by content and returns the same `data` object each time. A loose
    schema keeps nested objects such as `external`, so they must be cloned before anyone mutates
    them in the long-running app.
- **Copy the new fields through** `IssueSummary` (`types.ts:102`), `listIssues`
  (`storage.ts:404-415`, which doesn't copy `links` either), `issueToJson` (`json.ts:12-28`),
  `IssuePatchZ` / `NewIssueZ`, and `transferIssue`. `transferIssue` (`cross-repo.ts:227-250`)
  builds the moved issue key by key and also writes an old-format `at`.
- **Two `--json` shapes.** Only `hive ctl set-state` prints `issueToJson`. `hive show`,
  `update`, `close`, `reopen` and `link` print the raw `Issue`. The new fields go in both, and the
  shapes aren't unified here, so this is not a Breaking change.
- **No migration needed.** The change is additive. Old files read as before, and older builds
  ignore the new keys. Don't bump `WORKSPACE_FORMAT` (`storage.ts:257`), or older builds refuse
  the workspace.

### 5.2 Ids: the Jira key is the hive id

Mirrored issues use their Jira key (`PAY-318`) as their hive id:

- Branches, commits, PR titles and agent prompts all use the key the team already uses. GitHub
  for Jira links them with no extra work.
- Nothing is allocated from `next_id`, so mirrored and local issues never collide.
- **Prefix routing.** The workspace registers `PAY` as an *external prefix*, so `hive show
  PAY-318` from any repo resolves to it. Local issues keep the workspace's own prefix (`HIVEMI-3`).
  *P-R correction:* none of this exists yet.
  - Routing today is `rootForId` (`json.ts:34-46`): the local prefix, then the registry. Only
    the `hive ctl` issue verbs, `cross-repo.ts` and the desktop's `resolveIssueRoot` use it.
  - **`hive show`, `update`, `close`, `list` and `new` don't route at all** (`requireRoot()`
    only). P0d moves them onto `rootForId`.
  - The registry (`~/.config/hivemind/registry.json`) holds **one root per prefix**, and the
    last `registerWorkspace` wins (`registry.ts:83-88`). External prefixes therefore get their
    own map, `externals: {PAY: [root, …]}`, since two repos may mirror the same project.
  - Resolution order:
    1. The current workspace, when it owns the prefix (local or external).
    2. The only registered root.
    3. Otherwise exit 5 with every candidate listed. Never a guess.
  - A Jira project whose key equals the workspace's own prefix is refused at setup.
- **Key rules.** `IssueIdZ` is `^[A-Z][A-Z0-9]{1,9}-\d+`. Jira allows longer keys, and with an
  admin setting, underscores. Widen the regex to `^[A-Z][A-Z0-9_]{1,254}-\d+` for
  external-prefix ids only.
  - The pattern is copied in five places: `types.ts:28`, `storage.ts:226` (also the
    path-traversal guard), `registry.ts:104`, `apps/cli/src/parse.ts:46` and `IssuePanel.tsx:463`.
  - `links[].id` uses `IssueIdZ` too. P0d makes this one exported constant.
- **Sub-tasks.** They have their own Jira keys and are stored as separate issues with
  `parent: PAY-318`, not as dotted ids. Dotted ids stay for local sub-issues.
- **Key changes.** When an issue moves to another project, the key changes but `external.id`
  doesn't.
  - Sync matches on `external.id`.
  - It renames the file and keeps `aliases: [PAY-318]` so old references still resolve.
  - It writes an activity row.
  - The branch is not renamed.

### 5.3 Where mirrored issues live

`.hivemind/` is committed in many repos (this one commits `config.yaml`). If teammates each synced
their own "mine" scope into committed files, they would fight over merge conflicts. So:

- Mirrored issues live in **`.hivemind/mirror/<source-slug>/`**.
  - The folder is a slug of the source (`jira-acme-PAY`), not the source id. `jira:acme/PAY`
    can't be a folder name on Windows. The source id is kept in each file's `external.source`.
  - `hive init` and the plugin add `.hivemind/mirror/` and `.hivemind/sync/` to `.gitignore`.
    The CLI init (`init.ts:79-122`) writes only `.hivemind/.agent.md` there today, and the
    desktop `initWorkspace` (`main/index.ts` ~805) writes no `.gitignore` at all. Both paths
    change.
  - Each machine keeps its own mirror, and Jira holds the shared truth.
  - `listIssues` reads `issues/` and `mirror/**`. `issuePath`, `readIssue`, `deleteIssueFile`
    and `nextSubIssueId` assume `issues/`, so they move onto one id → path lookup that covers the
    mirror and `aliases`.
  - **The watcher must not rescan on sync bookkeeping.**
    - The desktop watches all of `.hivemind`, gitignored or not (`fs-watcher.ts:61-71`).
    - `issue-service.ts:50-60` reruns a full `listIssues` on any change. `listIssues` has no
      cache and re-parses every file (`storage.ts:392`).
    - A lock heartbeat or ledger write would otherwise re-list every issue in every open
      Issues tile.
    - P0d excludes `.hivemind/sync/` from that watcher and adds an mtime-keyed parse cache to
      `listIssues` (CLAUDE.md, "Work that runs per event").
  - **Writes become atomic.** `writeIssue` is a plain `writeFile` (`storage.ts:359`). Ingest
    writes a temp file and renames it, so a killed sync never leaves a half-written issue.
- Setting `mirror.commit: true` puts them in git instead, for single-person repos that want
  history.
- Sync state lives in `.hivemind/sync/<source>/`, gitignored:
  - `ledger.json`: `external.id → hive id`, plus the last remote `updated` and a hash of what was
    last written each way.
  - `schema.json`: the discovered workflow and fields.
  - `queue.jsonl`: pending pushes.
  - `lock`: single-writer.
- **One writer per workspace.** The service takes `lock` (pid + machine + heartbeat), built on the
  existing cross-process `holdLock` / `withLock` (`hive-core/src/settings.ts:282,291`). Only
  in-process locks exist on the issue path today (`allocChains`).
  - Services run in whichever process holds the drive socket: the app or `hive host`
    (`drive.ts:209-221`). That is one per machine, so the lock guards a clone against
    processes on the same machine.
  - Two machines with their own clones each sync their own mirror, as intended.
  - With `hive share`, guests see the host's result.

### 5.4 `hive ingest`: the one write path for every source

`hive ingest --source jira:acme/PAY [--dry-run] --json < records.ndjson`

Each line is a **normalised record**: provider-neutral fields plus `external.*`. Ingest upserts by
`(source, external.id)`:

1. **New** → it creates the mirrored file.
2. **Known, and remote `updated` is newer than the ledger** → it applies the fields Jira owns,
   which are listed in §8.1.
3. **Status:** it applies the conflict rule in §8.3.
4. **Unchanged hash** → it does nothing.

It reports `{created, updated, unchanged, conflicts, archived}`.

Ingest exists as a CLI command (`apps/cli/src/commands/ingest.ts`, which writes through core
directly, like every other issue command) and as a workspace-API method `issue.ingest` at the
`edit` role (§12), so a service can call it over the drive socket. Both call one core function,
`ingestRecords(root, source, records)`.

The REST service, the MCP transport and an agent holding a Jira connector all write through
ingest. Only the *reading* differs between them, so correctness lives in one place, with tests.

## 6. Discovery: learning a Jira

Discovery runs on connect, every 6 hours, and immediately whenever an issue comes back with a
status, issue type or field the schema doesn't know. The results go in `sync/<source>/schema.json`,
and `workflow.yaml` is regenerated from it.

### 6.1 What is discovered (REST v3; DC uses v2 equivalents)

*Verified 2026-10-24 (P-R):* every call below exists in Atlassian's OpenAPI specs (Cloud
platform v3 `1001.0.0-SNAPSHOT-12ca6ec5`, Software Cloud `1001.0.0`, DC 11.3.12) with the
parameters used. Permissions are from the operation descriptions. The scopes a scoped token
needs are in §9.1.

| Need | Call | Notes |
|---|---|---|

### 6.2 Adapting to each kind of Jira

| Shape | How it's handled |
|---|---|
| Company-managed, shared workflow scheme | Statuses per issue type from `/project/{key}/statuses`; several types can share one workflow |

When its `statuses` is empty, it's a placeholder and is dropped. Re-check on the live smoke.)* |
| No board / Jira Work Management | Columns = statuses ordered by category, then name; scope = project JQL |
| Several boards on one project | The person picks one in setup and can switch it |

| Data Center 8.x / 9.x | REST v2 (`/rest/api/2`), PAT bearer auth, wiki-markup rich text, no `/search/jql` (uses `/rest/api/2/search` with `startAt`), no team-managed projects |

### 6.3 The transition graph

When admin access allows it, the full workflow is read with `/workflows`. Otherwise the graph is
**learned**:

- Each pulled issue's `GET transitions` result is cached under `(issueType, fromStatus)` with a
  TTL of 24 hours, and again after any refused transition.
- Pathfinding (§8.2) uses the cache.
- An unknown edge triggers one live `GET transitions` for that issue before anything is decided.
- Live data always wins over the cache, because conditions are per issue and per user.

### 6.5 Rich text

- **Cloud v3** sends descriptions and comments as **ADF**, which is converted to markdown.

  - Rejected: `@atlaskit/editor-markdown-transformer` is md → ProseMirror only (its `encode()`

## 7. Pulling: scope, cadence, correctness

### 7.1 Scopes (a setting, editable in the tile)

| Scope | JQL (built per source) |
|---|---|
| **`mine`** (default) | `<base> AND assignee = currentUser()` |
| `mine+unassigned` | `<base> AND (assignee = currentUser() OR assignee is EMPTY)` |
| `all` | `<base>` |
| `jql` | the person's own JQL, AND-ed with the project |

`<base>` comes from the board type:

- **Scrum:** `project = PAY AND sprint in openSprints()`. A setting adds `OR sprint in
  futureSprints()`, or the backlog.
- **Kanban:** the board filter's JQL, with `statusCategory != Done OR updated >= -14d` so finished
  work fades out instead of piling up.
- **No board:** `project = PAY AND statusCategory != Done`.

Always add `AND issuetype not in (<excluded types>)`. By default this is empty. Epics are pulled
as parents, not as work items.

**What happens to issues that are not mine**
- When the scope is wider than `mine`, those issues are mirrored too, but marked
  `external.assignee.me: false`.
- The board's **assignee filter** defaults to **Me**. Its options are **Me**, **Unassigned** and
  **Anyone**, plus a person picker, and the choice is remembered per workspace.
- Cards not assigned to me show the assignee's avatar or an "Unassigned" chip.

**Browse without importing**
- The tile's **Browse** tab runs any scope or JQL live and shows the results without writing
  files.
- **Track** imports one issue, and so does starting work on it (§10).
- This avoids a mirror full of issues nobody here will touch.

**Shrinking the scope** (e.g. all → mine)
- Mirrored issues that are no longer in scope are **archived**: hidden, not deleted.
- The exception is issues with local work: a branch, a PR, or agent activity. Those stay visible
  with a "not in scope" chip.

### 7.2 Cadence

- **Incremental poll** every 60–300 s. It is adaptive: faster while the app is focused, slower
  when idle or when rate-limited.
  - JQL: `<scope> AND updated >= "<ledger high-water − 2 min>" ORDER BY updated ASC`.
  - It uses `POST /rest/api/3/search/jql` and pages with `nextPageToken`.
  - **Always pass `fields`**: it defaults to `id` only. Pass only what §6.4 needs.
  - Search embeds at most **20 comments and 40 changelog items** per issue (CHANGE-2046), so
    comments and history come from their own endpoints.
  - The response has `isLast`, a `nextPageToken`, and an experimental `warnings[]` that reports
    truncation. Warnings are logged and shown in the tile.
  - Data Center uses `/rest/api/2/search` with `startAt` (default page size 50).
- **Full reconcile** every 6 hours and on demand.
  - It fetches every id in scope with only `fields=updated,status,assignee` (`maxResults`
    up to 5000 for id-only pages).
  - It compares the result with the ledger to find issues that **left scope**, were **deleted**,
    or **lost access**, because an incremental poll never sees an issue that disappeared.
  - Ledger ids missing from scope go through `POST /rest/api/3/issue/bulkfetch`.
    - Batches are 1000 when `fields` names at most 100 single-value fields and there is no
      `changelog` / `transitions` expand; otherwise 100.
    - Issues that are missing or forbidden are **omitted**, and an omitted issue counts as deleted
      or no access (archived with that reason).
    - *P-R correction:* ids in **`issueErrors[]`** failed for a retriable or payload reason. They
      are retried on the next pass, **never archived**.
    - A returned issue under a different key has moved (§5.2). A returned issue still under its
      key has only left scope.
  - `POST /rest/api/3/jql/match` (10 queries × 50 ids) re-checks scope membership cheaply.
  - **Empty-scope guard.** An empty scope while the ledger is non-empty archives nothing. It is
    reported as "scope returned nothing". Since CHANGE-3131, a JQL clause that has turned invalid
    (a renamed field, a deleted sprint) returns zero results instead of an error, and that must
    not empty the mirror.
- **Comments:** fetched with `GET /issue/{key}/comment`, only for issues whose `updated` changed.
- **Changelog:** `POST /rest/api/3/changelog/bulkfetch` with `fieldIds: [status, assignee]` for
  the changed ids. It's only used to decide status conflicts (§8.3), not to rebuild history.
- **On demand:**
  - Sync now (tile).
  - `hive ctl plugin call @dip497/jira sync`.
  - Touching `.hivemind/sync/<source>/request`, which works even with the tile closed. Today a
    service can't answer `plugin call` (`docs/design/plugin-control-2026-10-16.md`).

### 7.3 Correctness traps

- **Time zones in JQL.** JQL date literals are read in the *user's profile time zone*, to the
  minute. Format the high-water mark in `myself.timeZone` and overlap it by 2 minutes. Ingest's
  hash check makes the overlap free.
- **Pagination.** Use the token-based `/search/jql`. The old `startAt` search on Cloud
  (`/rest/api/3/search`, `/rest/api/2/search`) returns **410 Gone** (CHANGE-2046). Page tokens
  expire after 7 days. There is no total count.
- **Eventual consistency.** Pass `reconcileIssues` (up to 50 ids) to make sure our own writes
  show up when we read straight after pushing.
- **Field ids** differ between sites and between team-managed projects. Never use a custom field
  by name after discovery.
- **Invalid JQL looks like an empty result** (CHANGE-3131, from 2026-06-29). Every built or
  person-written JQL goes through `POST /jql/parse?validation=strict` when it's built and after
  each discovery. A JQL that fails stops that scope's sync with the parser's message; it never
  reads as "nothing in scope".
- **Clock skew:** compare Jira's `updated` with Jira's `updated`, never with the local clock.
- **Issue security levels / restricted issues:** a 404 on a known issue means "no access", not
  "deleted". The mirror keeps the last copy as archived, with that reason.
- **Archived projects and issues:** treated as left scope.

## 8. Pushing to Jira (opt-in per source: `push: off | status | status+comments | full`)

### 8.1 Field ownership

| Field | Owner | Pushed when |
|---|---|---|
| title, description, type, priority, sprint, labels, components, parent, links | Jira | never. A local edit to these is refused for mirrored issues, with "edit in Jira" (opens the URL) |
| status | both | `push ≥ status` (§8.2, §8.3) |
| assignee | Jira | only through the start-work guard's "Assign to me" (§10), with `push ≥ status` |
| comments by people in hive, agent plan/summary, PR opened/merged | hive | `push ≥ status+comments`. Agent progress chatter is never pushed; a per-row-type allowlist lives in settings. |
| acceptance-criteria ticks | hive | `push = full`, and only when AC lives in a checklist the transport can write without losing anything |
| PR link | hive | remote link `POST /issue/{key}/remotelink` with `globalId: "github-pr:<org>/<repo>#<n>"` (≤255 chars), an idempotent upsert by `globalId` (§11.4). *Verified:* an update **sets every field you leave out to null**, so each push sends the whole link (title, url, icon, status). It needs *Link issues*, and answers 413 once the issue hits its per-issue remote-link cap. Jira has no public API that reads the PRs GitHub for Jira linked (dev-status is internal), so hive always writes its own link and reads PR state from GitHub. |
| sync metadata | hive | an entity property `PUT /issue/{key}/properties/hivemind` (`{hiveVersion, branch, pr, by}`, a JSON body of at most 32768 characters; needs *Edit issues*), read back through the `properties=hivemind` search parameter (5 properties at most), so teammates' installs see the work is underway. *Verified:* `POST transitions` takes `properties` too, so a move and its metadata land in one write, which matters under the per-issue write limit. *Still unverified:* whether a property write bumps `updated`; there's no doc and it needs the live test. The ledger records the `updated` that each of our own writes returns and ignores it either way. |

### 8.2 Status → transition

Jira can't set a status directly. To move to target status `T`:

1. **Hive-only target.** If `T` is hive-only (`source: hive`), set it locally. Then, if
   `jira.follow` names a Jira status, apply steps 2–5 for that status instead. If it says `stay`,
   Jira isn't touched.
2. Fetch the issue's live transitions.
3. If one goes directly to `T`, use it.
4. Otherwise find the **shortest path** in the learned graph, at most 3 hops. Each hop's
   transitions are fetched live before the hop is taken.
   - Auto-taking multi-hop paths is a setting, default on for paths that need no screens.
   - For other paths the person is shown the path and confirms it.
5. **Screens / required fields.** `hasScreen` tells whether a screen applies, and
   `transitions.fields[*].required` lists what it needs (e.g. resolution). Fields are fetched
   with `expand=transitions.fields`.
   - Hive shows a form built from the field metadata, pre-filled from per-transition defaults in
     settings.
   - `resolution` is sent only when it appears in `transitions.fields`.
   - A required field that isn't on the screen comes back as a 400 `errors{}`. Its message is
     shown, and the field is remembered for next time.
   - Agents can't fill screens. Their move stops at the last step that needs none and is flagged
     for the person.
6. **Refused (validator or condition):** the local status is put back, the issue's activity gets
   Jira's error message, and a toast offers to open it in Jira.
   - The POST answers 400 for a refused condition or a missing field.
   - **409** means a concurrent update: retry after a delay.
   - **422** means a workflow misconfiguration: show it, and don't retry.
   - **413** means a per-issue limit was hit, for comments, links or remote links.
   - (Status codes from the spec and CHANGE-1364/1877.)

Pushes are queued (`sync/<source>/queue.jsonl`), debounced 5 s, and merged per issue: the last
target wins. A failed push is retried with backoff and survives restarts. While a push is pending,
the card shows a "syncing" mark.

### 8.3 Status conflicts

Both sides changed status since the last sync (the ledger holds the last synced remote status and
the last local change):

- **Remote moved, local didn't** → take the remote status.
- **Local moved, remote didn't** → push.
- **Both moved to the same status** → nothing to do.
- **Both moved to different statuses:**
  - If the local move was *only* into a hive-only status whose `follow` equals the new remote
    status, they agree.
  - Otherwise this is a **conflict**: the card gets a mark, and the tile's Conflicts list shows
    both sides with "Keep Jira" / "Keep hive". The default after 24 h is Keep Jira.
- **Remote reached `done` or `cancelled` while local work exists** (branch / PR) → take the remote
  status. Tell the person; never close their PR.

## 9. Transports

### 9.0 Decided 2026-10-24 (supersedes the transport order below where they differ)

- **Jira Cloud only.** Data Center is deferred: the `JiraTransport` interface and its capability
  flags keep room for a v2/PAT transport, but only the Cloud (v3/ADF) fixtures are built and
  tested. The DC notes in §6–§9 stay as reference for that later work.
- **Auth, in the wizard's order:**
  1. **"Sign in with Atlassian" (default):** the Rovo MCP server (§9.2), with OAuth 2.1, dynamic
     client registration, PKCE and a loopback redirect, through `@modelcontextprotocol/client` or
     `@modelcontextprotocol/sdk`. Tokens go in the `secret` setting type (§12.3).
  2. **Scoped API token (alternative):** REST against `api.atlassian.com/ex/jira/{cloudId}`
     (§9.1), for heavy use, or when the org blocks the MCP sign-in. API-token traffic is exempt
     from the points quota.
  - **No OAuth 3LO** (§9.1 says why).
- **The service syncs; no agent, no LLM tokens.** The plugin service is a deterministic MCP
  client (or REST client when a token is set). It polls every 1–5 min, adaptively. Both
  transports go through `JiraTransport` and `hive ingest`.
- **MCP budget.**
  - At most 3 MCP calls in flight.
  - An hourly call budget (a setting, default 400/h) that pull and push share, because the Rovo
    hourly limit may be shared org-wide (§9.2). The poll interval stretches to stay under it, and
    the tile shows the budget.
  - Every MCP response is validated against our own schema.
- **Missing capabilities.** When MCP lacks a capability (bulk changelog, `/field`, `jql/parse`,
  entity properties in search, the workflow graph), the service uses REST if a token is also
  configured. Otherwise it degrades the way §9.2 says and shows the reason.
- **The `jira` agent skill** (§9.4) ships with preset prompts on top of the service, and writes
  only through `hive ingest`.
- **Phases:** P0 → P1 → P2 (MCP transport + sign-in + pull) → P2b (REST/token transport) →
  P3 (push) → P4 (the skill) (§16).

All transports implement one interface inside the plugin:

```ts
interface JiraTransport {
  capabilities: { workflowGraph: boolean; changelog: boolean; adf: boolean; fieldsMeta: boolean; agile: boolean; entityProps: boolean; push: boolean };
  discover(): Promise<Schema>;
  search(jql: string, fields: string[], pageToken?: string): Promise<Page<RawIssue>>;
  issue(idOrKey: string): Promise<RawIssue | Gone>;
  comments(key: string, since?: string): Promise<RawComment[]>;
  transitions(key: string): Promise<Transition[]>;
  transition(key: string, id: string, fields?: object): Promise<void>;
  assign(key: string, accountId: string | null): Promise<void>;
  comment(key: string, markdown: string): Promise<{ id: string }>;
  remoteLink(key: string, link: RemoteLink): Promise<void>;
}
```

The sync engine (scope, ledger, ingest, queue, conflicts) never knows which transport it's
talking to. Features a transport can't support are turned off in the UI, with the reason shown.

### 9.1 REST (the alternative: a scoped API token; §9.0)

*Verified 2026-10-24 (P-R)* against the token, 3LO and rate-limiting pages (each updated
2026-10-23) and the Jira changelog.

- **Cloud, API token (default).**
  - Classic (unscoped): Basic `email:token` against `https://<site>.atlassian.net`.
    - *Corrected:* there is **no announced deprecation** of unscoped tokens. The token page
      only recommends scopes.
    - Unscoped stays the simplest default, since it needs no cloudId and covers Agile.
  - Scoped (recommended by Atlassian): Basic `email:token` **only** against
    `https://api.atlassian.com/ex/jira/{cloudId}`. The site URL rejects them, with a 401.
    - **The cloudId** comes from `https://<site>.atlassian.net/_edge/tenant_info` (documented in
      Atlassian's KB, not as an API). If that fails, the wizard asks the person to paste it.
    - **Scopes**, from the specs' `x-atlassian-oauth2-scopes`:
      - Platform (classic is fine): `read:jira-work`, `write:jira-work`, `read:jira-user`.
      - The optional admin workflow graph: `manage:jira-configuration` (classic) or
        `read:workflow:jira` (granular).
      - **Agile accepts granular scopes only:** `read:board-scope:jira-software`,
        `read:board-scope.admin:jira-software` (board configuration and features),
        `read:project:jira`, `read:sprint:jira-software`, and `read:issue-details:jira` +
        `read:jql:jira` for `/rest/software/1.0` listings.
      - A token with only classic scopes gets 401 "scope does not match" on Agile.
      - Community sources report at most 50 scopes per token.
    - The wizard tests a board call before saving, and names any missing scope.
  - Tokens expire after 1–365 days (since 2024-12-15). The token's age can't be read through the
    API, so the wizard asks for the expiry date, and the tile warns 14 days before it.
  - **API-token traffic is exempt from the points quota**; only the burst limits apply (burst
    limits have applied to API tokens since 2025-11-22, CHANGE-2578). That's the main reason it's
    the default.
  - **Distribution risk:** the 3LO page says "apps that collect API tokens or instruct customers
    to create individual 3LO apps don't comply". That targets Marketplace and Connect apps, not a
    local desktop client using the person's own token. It's noted for when we publish anyway.
- **Cloud, OAuth 2.0 (3LO).** **Deferred.**
  - It needs a client secret for both the code exchange and refresh, and **Cloud has no PKCE**
    (ECO-283).
  - Its traffic also counts against an app-wide 65k points/hour pool shared by every user.
  - It needs a secret-holding broker. The MCP path below gives "sign in with Atlassian" without
    one.
- **Data Center:** a Personal Access Token as `Bearer` (Jira 8.14+), REST v2 plus
  `/rest/agile/1.0`. Rich text is wiki markup, search uses offset paging, and users are
  usernames. DC reaches end of life on 2029-03-28. **Decided 2026-10-24: Cloud and DC are both
  first-class from the start.** Every phase is tested against both fake-Jira variants: Cloud
  v3/ADF/accountIds, and DC v2/wiki/PAT/usernames (`cloud-*` and `dc-v2-wiki` sites).
- **Rate limits.**
  - Burst limits: GET/POST 100/s, PUT/DELETE 50/s per endpoint.
  - **Per-issue writes: 20 per 2 s and 100 per 30 s.** The push queue merges writes per issue
    and spaces them out.
  - Honour `Retry-After`. Read `RateLimit-Reason`:
    - a quota reason (`jira-quota-global-based`, `-tenant-based`) pauses everything until the
      reset;
    - `jira-burst-based` slows only that endpoint;
    - `jira-per-issue-on-write` delays writes to that issue only.
  - `X-RateLimit-NearLimit` (under 20% left) turns the poll rate down.
  - Atlassian will replace `X-RateLimit-*` with `RateLimit` / `RateLimit-Policy` (currently
    sent `Beta-`-prefixed). Read both.
  - At most 4 requests in flight. Backoff is jittered (×0.7–1.3), starting at 2–5 s, capped at
    30 s, with 4 retries. Only **idempotent requests that carry `Retry-After`** are retried
    automatically (Atlassian's own rule). Any other failed write goes back to the push queue.
  - The tile shows "rate-limited, next try 14:02".

### 9.2 MCP: the Atlassian Rovo MCP server (the default since §9.0)

*Re-checked 2026-10-24 (P-R)* against the Rovo MCP docs (supported tools page, updated
2026-09-30), the repo README and the changelog.

- **Endpoint.** `https://mcp.atlassian.com/v2/mcp?tools=all` (Streamable HTTP; v2 GA 2026-09-08,
  CHANGE-3431).
  - `?tools=all` is documented "for MCP gateways". It lists tools flat instead of through
    discover/execute, **paginated 50 to a page**, so `tools/list` follows the cursor.
  - `/v1/sse` has been unsupported since 2026-06-30, and from 2027-03-01 v1 traffic gets v2 tools.
  - Tool names change: `findJiraIssueAssignableUsers` became `listJiraIssueAssignableUsers`
    (CHANGE-3452). So the transport finds tools by capability through `tools/list`, using a name
    table it can update.
- **Auth.**
  - OAuth 2.1 with dynamic client registration and PKCE, through a **loopback redirect**:
    `http://127.0.0.1:*/**` is in Atlassian's default allowlist for MCP clients. That gives "sign
    in with Atlassian", and no developer app is needed.
  - Or an **API token**, which an org admin must turn on (Administration → Rovo → Rovo MCP server
    → Authentication).
    - *Corrected:* the token **must be scoped** with `read:jira:agent-interface`,
      `write:jira:agent-interface` and `search:jira:agent-interface`.
    - It is sent as Basic `base64(email:token)`. A service account uses `Bearer <key>`.
    - `cloudId` is passed as a **tool argument**.
    - Only the IP allowlist applies.
  - **Don't cache** the registered `client_id` or the `.well-known` discovery document: DCR moved
    to the Atlassian Identity auth server on 2026-05-27 (CHANGE-3170).
  - **Token lifetime is undocumented.** Issues report access tokens lasting about an hour, refresh
    tokens dying after about 4 idle days on v2 (#260), and stale grants showing up as 403 "app
    not installed" (#283). All three are treated as "sign in again", with a tile prompt and never
    a crash loop.
- **Client.** The official TypeScript MCP SDK (`@modelcontextprotocol/client` v2, or
  `@modelcontextprotocol/sdk` v1), using `StreamableHTTPClientTransport` and an
  `OAuthClientProvider`. Tokens go into `secret` storage.
- **Tools used:**

  | Purpose | Tools |
  |---|---|
  | Site and user | `getAccessibleAtlassianResources`, `getJiraCurrentUser` |
  | Search and fetch | `searchJiraIssuesUsingJql`, `getJiraIssue` |
  | Statuses and transitions | `listJiraStatuses`, `listJiraIssueTransitions`, `transitionJiraIssue` |
  | Comments and changelogs | `listJiraIssueComments`, `addOrEditJiraIssueComment`, `listJiraIssueChangelogs` |
  | Boards and sprints | `listJiraBoards`, `getJiraBoardConfig`, `listJiraBoardSprints`, `getJiraBoardIssueData`, `getJiraBoardSprintData` |
  | Fields | `getJiraIssueTypeMetaWithFields`, `listJiraProjectIssueTypesMetadata` |
  | Assignable users | `listJiraIssueAssignableUsers` (was `findJira…`), `lookupJiraAccountId` |
  | Writes | `editJiraIssue` (assign), `createJiraIssueRemoteIssueLink`, `getJiraEntityProperty` / `editJiraEntityProperty` |

  All of these are in the default `read_jira` / `write_jira` / `search_jira` groups (verified).
  `getJiraWorkflows` is in `manage_jira`, which is off by default.

- **Limits that make it second choice:**
  - **Rich text is markdown only**; ADF requests are ignored. So `capabilities.adf = false`, and
    description pushes are off.
  - **Output shape.** It is semi-structured. `structuredContent` was seen withheld from clients
    whose `clientInfo.name` isn't recognised. Every response is validated against our own schema,
    and anything that doesn't match fails loudly instead of being guessed at.
  - **The full workflow graph needs the admin-gated `manage_jira` tools**, so the learned graph
    (§6.3) is the norm here.
  - **No bulk changelog and no fields search.**
  - **Rate limits.** Hourly limits by plan aren't officially published (still unverified; the
    figures in circulation are third-party). 429s have been reported at about 20 parallel calls,
    with only `Retry-After` returned (#171, open), so cap concurrency at 3.
  - **Credits.** `search` (Rovo semantic search) "may consume up to 10 Rovo credits per call",
    and overage billing starts 2026-12-03. So it is **never used**; JQL tools only.
  - **`structuredContent` gating** for unrecognised clients was seen on v1 (#213, open) and is
    unverified on v2. The P4 contract test records a real v2 session with `clientInfo.name:
    "hivemind"` and settles it.
- **When to choose it:** the org disallows API tokens but has OAuth MCP enabled, or the person
  wants "sign in with Atlassian".

### 9.3 MCP: self-hosted `sooperset/mcp-atlassian` (deferred with Data Center, §9.0)

- MIT licence, Python (uvx/Docker), stdio transport, JSON text output.
- It has bulk changelogs, field search, agile tools and development info.

### 9.4 The `jira` agent skill (preset prompts on top of the service)

*Decided 2026-10-24:* the skill ships with the plugin, with preset prompts: **import an epic**
(`PAY-300` and its children), **triage a sprint**, **start an issue** (through the §10 guard) and
**complete an issue** (§11.2). It asks the service through `hive ctl plugin call @dip497/jira …`
when one is running, and otherwise reads Jira over the agent's own connector. Either way it writes
only through `hive ingest`, under the guardrails below.

- An agent tile that holds the Atlassian connector (Claude, Cursor, …) reads Jira over MCP and
  writes **only** through `hive ingest`. The skill `jira-import` (shipped with the plugin) carries
  the record format and the rules.
- Good for: a one-off import, "pull epic PAY-300 and its children", triage. Not continuous sync:
  it costs tokens, it isn't scheduled, and issue text could carry prompt injection.
- **Guardrails:**
  - Ingest validates every record.
  - An agent can't push to Jira through ingest; pushes go through the service or the person.
  - Ingest doesn't do anything an issue's text tells it to.

### 9.5 Why no webhooks

- A desktop app has no public URL.
- Dynamic webhooks are only for OAuth / Connect apps. They expire after 30 days (extendable with
  `PUT /rest/api/3/webhook`), there are 5 per app per user per tenant, and they need public HTTPS
  with a trusted certificate, not on port 80 (verified 2026-10-24).
- A relay (a Forge app, or a tunnel) would add a hosted piece and an account to run it.
- Polling with incremental JQL is cheap enough at sprint scale.
- **Later:** a `hive host` on a reachable server could take webhooks and treat each one as a hint
  to poll now. It would never be the source of truth.

## 10. The start-work guard

`checkStartWork(issueId, actor)` lives in hive-core, so the CLI can call it with no host
running. Trackers add their checks through a provider hook. It runs before every way of starting
work (*entry points verified on origin/main, 2026-10-24*):

- **The UI's "Work on this":** `IssuesTile.tsx:97-123`, which calls
  `hm.commands.spawnAgent(...)` and reaches the renderer's `spawnTile` (`Workspace.tsx:1261`).
  It doesn't go through the host's `agent.start`, so the renderer path needs its own call.
- **Dragging to an `in_progress`-category status:** `BoardView.tsx:31-47`, then `issue.setState`
  in `host/src/issues.ts`.
- **`hive ctl set-state … in_progress`** (`ctl.ts:633`) **or `hive update --status <in-progress
  status>`** (`update.ts:41`). Both write through core directly.
- **`hive ctl spawn --issue`.** This flag is new in P1; the command has no issue flag today. It
  goes through `agent.start` (`host/src/agent-control.ts:136`).
- **`hive ctl workflow` with issues as items.** Items are plain strings, run client-side in
  `apps/cli/src/workflow.ts`. The guard runs before `start()` (`:41-56`) and fills a new
  `skipped[]`.

It **re-fetches the issue live** when the last sync is more than 60 s old, then checks:

| # | Check | Severity | Offered actions |
|---|---|---|---|
| 1 | Jira assignee is **nobody** | warn | **Assign to me and start** · Start without assigning · Cancel |
| 2 | Jira assignee is **someone else** | warn (strong) | Start anyway (posts "picked up in hivemind by …" if comments are pushed) · Assign to me and start (needs `ASSIGN_ISSUES`) · Cancel |
| 3 | Status category is already `in_progress`, by someone else | warn | as #2 |
| 4 | Status category `done` / `cancelled` | warn | Reopen (if a transition exists) · Cancel |
| 5 | Not in an active sprint (backlog / future sprint) | info | Start anyway · Cancel |
| 6 | Blocked by an unresolved issue (`is blocked by` link) | warn | Start anyway · Open blocker · Cancel |
| 7 | Flagged / impediment | warn | Start anyway · Cancel |
| 8 | No permission to transition (`TRANSITION_ISSUES`) or be assigned (`ASSIGNABLE_USER`) | info | Start locally only (no Jira push) · Cancel |
| 9 | Sub-task whose parent is done, or epic closed | info | Start anyway · Cancel |
| 10 | Another hive install is already on it (entity property `hivemind.branch` from someone else, §8.1) | warn | Start anyway · Cancel |
| 11 | An agent tile here is already working this issue | block | Focus that tile · Cancel |

**Surfaces**
- **UI:** one dialog listing every finding, with the actions above. Checking "Don't warn me for
  unassigned issues in this workspace" turns off #1 only.
- **CLI / agents:** refuses with exit **7**, `code: "NEEDS_CONFIRM"` and `warnings: [{check,
  message, actions}]`.
  - Exit 7 is already the "refused" row (`RATE_LIMITED`, `DEPTH_EXCEEDED`, `UNSUPPORTED`,
    `OCCLUDED`, `PART_OF_A_PACKAGE`; `apps/cli/src/exit-codes.ts:10-21`). `NEEDS_CONFIRM` joins
    that row, since agents branch on `code`, not on the number.
  - `NEEDS_CONFIRM` is added to `ErrorCode` (`workspace-api/src/protocol.ts:8-41`) and to the
    exit-code table.
  - The failure JSON `{code, message, fix}` gains an optional `warnings`. That is additive, so
    it isn't Breaking.
  - `--assign-me` does "Assign to me and start".
  - `--ack <check,…>` acknowledges specific checks, for example `--ack unassigned`.
  - `--force` acknowledges every warn-level finding. Block-level findings can't be forced.
  - The agent skill says: **ask the person, never `--force` on your own.**
- **`hive ctl workflow`:** runs the guard on every item first. Items with findings are left out
  and listed under `skipped[]`, unless the caller passed `--ack`.

**Who is "me"**
- Jira's assignee is the **person** whose token or OAuth the sync uses (`myself.accountId`).
- Hive's `assignee` is the **agent** doing the work.
- "Assign to me" sets the Jira assignee to the person. Agents never become Jira assignees.

## 11. Branch, worktree, PR

### 11.1 Start

After the guard passes:

1. Creates or reuses the branch `<KEY>-<slug>` (`settings: branchTemplate`, default
   `{key}-{slug}`).
2. Creates the worktree and opens it as a worktree frame.
   - The frame comes from `frame.open(repo, {worktree: {branch, base}})`
     (`packages/host/src/frames.ts:146-160`). It reuses or creates the worktree through
     `worktreeCreate` (`packages/host/src/git-adapter.ts:688`) and works headlessly too.
   - The default location is `../<repo>-worktrees/<slug>` (`git-adapter.ts:705-708`).
   - `worktreeCreate` refuses a branch that is already checked out (`:711-716`). Reusing a
     branch means finding its existing worktree first.
   - P1 adds `--worktree <branch>` to `hive ctl frame add`, which today offers only `--folder`
     and `--machine`.
3. Writes `branch:` on the issue.
4. Moves the issue to the workflow's start status (§8.2) and pushes it.
5. Spawns the agent in that frame with `tile.issue = "<KEY>"`, a structured field rather than
   just prompt text.
   - **New in P1.** `TileRecord` (`workspace-doc/src/shapes.ts:44-61`) and `StartAgent`
     (`workspace-api/src/agents.ts:115-130`) have no issue field today.
   - It is added to both, to `startOf` in `agent-control.ts`, and to `spawnAgent` options
     (`view-host/src/link.ts:46`).
   - It is not added to `RUNS` (`workspace-host/src/edit-rules.ts:24`), so peers can't rebind
     a tile.
6. Gives the agent a prompt built from the issue: description, AC and links. It ends with the
   §11.2 contract.
   - The prompt is built today by `workPrompt` (`IssuesTile.tsx:97`).
   - Mirrored text goes in fenced as quoted material (§14).

### 11.2 Agent contract (replacing "Do NOT push", step 6 of `HIVE_WORK_SKILL` at `hive-core/src/templates.ts:178`)

- Commit as `<KEY>: …`, and end with `hive ctl complete <KEY>`.
- `complete` checks:
  - the tree is clean and the branch has commits ahead of base;
  - the AC are ticked, or there's an `--ac-note` explaining why not;
  - the local tests, if `config.yaml` names a check command.
- Then, by workspace policy. **Decided 2026-10-24: the default is `pr`.** Finishing pushes the
  branch, opens the PR (`hive pr create`) and moves the issue to `local.onPrOpened` (PR Created).
  `review` is the opt-out, and `draft_pr` opens a draft.

```yaml
# .hivemind/config.yaml (needs ConfigZ to keep unknown keys, §5.1)
on_complete: pr          # pr (default) | draft_pr | review   (review = the opt-out: today's behaviour, moves to the in_review category)
pr_base: main
pr_gate: none            # none | approve  (approve blocks on `hive ctl open-review` before the PR opens)
cleanup: ask             # ask | auto | never  (worktree + local branch after merge)
```

### 11.3 `hive pr`

| Command | Does |
|---|---|
| `hive pr create <KEY> [--draft] [--base]` | Pushes `-u`, then runs `gh pr create`. Title: `<KEY>: <title>`. Body: summary, AC checklist, Jira link, agent's completion summary. Writes `pr` + `github`, then moves to `local.onPrOpened`. |
| `hive pr status <KEY>` | `gh pr view --json state,mergedAt,reviewDecision,statusCheckRollup,url` |
| `hive pr sync` | The watcher's single pass, for scripts |

- **Auth:** `gh` is the auth. When `gh auth status` fails, the command says how to fix it and moves
  the issue to the `in_review` category with a note. Nothing hangs, and no GitHub tokens are
  stored.
- **Remote tiles:** a tile on a remote machine uses that machine's `gh`, the way `git` runs there
  (`packages/host/src/remote/git.ts`, over `remote/exec.ts`).
- Today the repo's only `gh` use is `gh api user` (`apps/cli/src/commands/plugins.ts:316`), and
  `github:` is display-only (`#N`). All PR code is new.

### 11.4 PR watcher (host side, so it runs under `hive host` too)

The host has no generic scheduler today. There are only ad-hoc `setInterval`s, and headless uses
`fs.watchFile`. P1 adds a small one in `packages/host`, started from both
`apps/desktop/src/main` and `headless.ts`. Following the per-event rules in CLAUDE.md, it stops
when no issue has an open PR.

Every 3 minutes it checks every issue with `pr.state: open`, batched in one `gh api graphql` query:

| PR event | What hive does |
|---|---|
| **merged** | moves to `local.onPrMerged` (pushed as a transition), offers cleanup |
| **closed, not merged** | moves to `local.onPrClosed`, with a note and a notification |
| **changes requested** | stays put; the card shows a badge; "Address review" spawns an agent in the same worktree with `gh pr view --comments` |
| **checks failing** | badge; "Fix CI" does the same as above with the failing logs |

The remote link on Jira carries the PR URL. When the PR is merged, the link's status is updated
to resolved.

## 12. Core platform additions (for any plugin, not only Jira)

*Verified against origin/main on 2026-10-24 (P-R). P0c is larger than rev 3 said.*

1. **`issue.changed {id, root, fields, by}`** on every write, from the CLI, an agent, the window or
   a peer. This is Phase 0 item 1 of `docs/design/plugin-platform-2026-10-03.md` §7, brought
   forward.
   - **No such event exists today.** Views learn of changes from the desktop's chokidar
     `file.changed` (`main/fs-watcher.ts:45-127`). It reaches window IPC only, never
     drive-socket peers, and `hive host` runs no watcher at all.
   - **The CLI writes issue files directly through core**, bypassing the host. A hook only in
     `host/src/issues.ts` would therefore miss every CLI and agent write. The source of the event
     is a host-side watcher on `.hivemind/issues` and `.hivemind/mirror`: the part of
     `fs-watcher.ts` that applies, moved into `packages/host` so headless gets it too. It diffs
     against the parse cache (§5.3) to fill `fields`, and `by` comes from the file's last
     activity row.
   - **The event must be repo-scoped.** An event missing from the list at
     `workspace-api/src/peers.ts:203` is sent to every peer (`:215-217`).
   - The Issues tool moves from `file.changed` onto `issue.changed`.
2. **Issue writes for services.** `issue.create`, `issue.update`, `issue.setState`,
   `issue.comment` and `issue.ingest` open to the `edit` role in
   `packages/workspace-api/src/roles.ts`. Today only `issue.list` and `issue.read` are open to
   non-owners (`:25-26`), and everything unlisted is owner-only. Grants are never owner.
   - **Policy note:** this also lets `edit` guests (people a workspace is shared with) write
     issues. That matches what `edit` means elsewhere, and it goes in the CHANGELOG.
   - Activity is signed `"ui"` whatever the caller (`host/src/issues.ts:37-49`). It is signed
     with the caller's actor instead, e.g. `@dip497/jira (service)`, and
     `host/tests/workspace-api.test.ts:57` changes with it.
3. **`secret` setting type**, stored with Electron `safeStorage` (the same pattern as
   `apps/desktop/src/main/remote/saved-hosts.ts:39-53`).
   - Setting fields are `boolean | number | text | choice` today
     (`hive-view-sdk/src/settings.ts:17-21`). P0c adds `secret` to the type, the parser,
     `fitValue` and `SettingsForm.tsx`.
   - The UI never echoes the value, and `settings.json` keeps only a reference.
   - The value is never put in `hm.settings`. `hive plugins set` refuses a secret as an
     argument and reads it from stdin instead.
   - A service reads it through a new drive method, `secret.get`, limited to the grant's own
     plugin. Grants already record their plugin (`grants.create(…, want.plugin)`).
   - `hive host` has no Electron, so it falls back to a 0600 file (written to a temp file and
     renamed, as in `host/src/grants.ts:120-125`) and says so.
4. **A service reads its own options.** This was missing from rev 3: a service has no way to read
   its plugin options today, short of reading `settings.json` off disk. P0c adds
   `plugin.options` (read, own plugin only) on the drive socket. Changing a setting doesn't
   restart a service (`services.ts:242`), so the service re-reads it on an `options.changed`
   event.
5. **Services answer commands.** `hive ctl plugin call` reaches the service when no tile is open.
   - Today the path is CLI → `control/methods.ts:1141` → `callRenderer("plugin.call")`, which
     reaches tiles, views and widgets only. Under `hive host` it fails with UNAVAILABLE.
   - P0c adds:
     - a `plugin.serve` notice by which a service registers its commands on its drive
       connection;
     - a host registry keyed by plugin id;
     - `pluginCall` trying the window first, then the service, as a request/answer pair over
       that connection;
     - a `roles.ts` entry, since `MACHINE` (`:111`) gates `plugin.*` to tiles.
   - This is also the **tile ↔ service channel**: a grant can't `view.emit`, so the Jira tile
     asks the service by `plugin call`. Until this lands, the request file in §7.2 stands in.
6. **Workflow read** in the view SDK and the workspace API (§4.3).
7. **Packaging constraint for services.** HiveHub installs only the listed files: there's no
   npm install, and the caps are 20 MB a file and 50 MB in all
   (`hive-core/src/plugin-catalog.ts:88-115`).
   - So the Jira service is **one bundled `.mjs`** (esbuild), with the MCP SDK inlined.
   - It runs with `node` from PATH (`services.ts:96` refuses `.cmd` shims).
   - People who installed the prebuilt app may have no `node`. P0c makes `node` in a service
     command fall back to the host's own runtime (Electron with `ELECTRON_RUN_AS_NODE=1`), so
     they don't need one. `hive host` checks for `node` on PATH and names the fix when it's
     missing.
   - The service log appends raw stdout (`services.ts:159`), so the service redacts
     `Authorization` itself.

## 14. Security and privacy

- **Tokens** are only ever in `secret` storage. They never appear in issue files, logs (the service
  log redacts `Authorization`), `settings.json` or the agent's environment.
- **Agent tiles get no Jira credentials.** Agents act on Jira only through hive commands, which
  the service carries out.
- **Mirrored issue text is untrusted.** It is shown, never run. When it goes into agent prompts it
  is fenced as quoted material, and the skill says so.
- **Mirrors are gitignored by default** (§5.3), so private ticket text isn't pushed to a repo by
  accident.
- **Pushes** are opt-in, and every write to Jira is recorded in the issue's activity
  (`who: hive→jira`).

  The sync engine's unit tests run against it, and the transport contract tests run against both

- **e2e (Playwright):**
  1. Wizard → first sync → board columns match the fixture's board.

  3. Start an unassigned issue → dialog → assign → spawn.
  4. Complete → PR (with a `gh` shim) → merge → Done.
