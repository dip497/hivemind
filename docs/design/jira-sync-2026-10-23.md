# Jira sync: any Jira workflow, mirrored into hive, from sprint to merged PR

Status: proposed, revision 3, 2026-10-24. Code references are to `origin/main`.
Research notes (endpoints, auth, limits, MCP, with sources): `jira-sync-research-2026-10-24.md`.
Anything marked UNVERIFIED there gets confirmed in phase P-R before it's built on.

## 1. Goal

A hivemind workspace linked to Jira works the same Jira the team already uses:

- **Every status, in every workflow, is mirrored.** This covers company-managed and team-managed
  projects, Scrum, Kanban and simple boards, a different workflow per issue type, and Cloud and
  Data Center. The hive board shows Jira's own columns and statuses, plus the hive-only statuses
  the team adds (e.g. **PR Created**). Both exist side by side.
- **By default it pulls issues assigned to me.** A switch pulls everything, and the person can
  browse the rest. Starting work on an issue that is unassigned, or assigned to someone else,
  asks first.
- **Agents work issues on their own branches.** Finishing opens a GitHub PR, the issue moves to
  PR Created, and merging moves it to Done. Every move goes back to Jira as a legal transition.
- **The transport can be swapped.** REST is the default. The Atlassian MCP server is an option,
  and so is an agent with a Jira connector. All three write through the same deterministic
  ingest path.

```
Jira (any workflow) ──discover──▶ hive workflow (Jira statuses + hive-only statuses)
        │                                   │
        └──pull (mine | all | jql)──▶ mirrored issues ──start (assignment guard)──▶ branch + worktree + agent
                                            │                                                  │
                            Jira transition ◀── every status change ◀── PR created ◀── agent completes
                                                                         │
                                                         PR merged ──▶ Done ──▶ Jira transition
```

### Non-goals (for now)

- Editing Jira workflows from hive. Hive adapts to the workflow and never changes it.
- Jira Service Management queues and SLAs, worklogs/time tracking, attachments (we link them,
  we don't download them), Confluence.
- Webhook delivery to the desktop (there's no public URL; see §9.4).

## 2. Principles

1. **Learn the workflow from Jira; never hardcode it.** Statuses, categories, transitions, board
   columns and custom fields are read from Jira and cached. Whatever Jira returns that we didn't
   expect gets a sensible default and a visible note, never a crash.
2. **Jira owns its fields; hive owns its own.** A field has exactly one owner, and the one field
   both sides write (status) follows a written conflict rule.
3. **Sync is deterministic and idempotent.** Re-running any sync changes nothing. A sync killed
   halfway and restarted produces no duplicates and loses nothing.
4. **Nothing is lost.** Hive never deletes a mirrored issue because Jira stopped returning it. It
   archives the issue and says why.
5. **No surprises for the person.** Hive warns before acting on someone else's or nobody's issue.
   It never pushes to Jira without the opt-in. Every write it makes to Jira shows up in the
   issue's activity.
6. **Core stays tracker-neutral.** Jira is a plugin. Linear, GitHub Issues and others reuse the
   same core contract.

## 3. Architecture

| **Core** (ships with hivemind; tracker-neutral) | **Jira plugin** `@dip497/jira` (HiveHub tool package) |
|---|---|
| Per-workspace **workflow** (dynamic statuses with categories), §4 | Discovering the Jira workflow, board and fields, §6 |
| `external` link, mirrored-issue storage, keys as ids, §5 | Pull scopes, JQL building, incremental polling, §7 |
| **`hive ingest`**: deterministic upsert that every source writes through, §5.4 | Push queue: transitions, comments, assignee, remote links, §8 |
| **Start-work guard** (assignment and readiness checks), §10 | Transports: REST / Rovo MCP / self-hosted MCP, §9 |
| Issue → branch → worktree → PR lifecycle, PR watcher, §11 | ADF ↔ markdown, §6.5 |
| `issue.changed` events; issue writes for services; `secret` settings, §12 | Sync tile (status, mapping, conflicts, browse), §13 |

The plugin runs as a tool-package **service**: a long-lived Node child of the host, with its own
drive grant, restart backoff and a log file (`packages/host/src/services.ts`). Next to it sits a
**tile** for the UI. Both exist on main today. §12 lists what core has to add.

## 4. Core: a workflow per workspace

### 4.1 Model

The six fixed states become **categories**. A workspace defines **statuses**, and each status
belongs to one category:

| Category (stable contract) | Jira `statusCategory` default | Meaning to hive |
|---|---|---|
| `backlog` | `new` and not on the board / in backlog | not planned |
| `todo` | `new` | planned, not started |
| `in_progress` | `indeterminate` | someone is on it |
| `in_review` | `indeterminate` whose name looks like review/QA/test (a heuristic the person can edit) | work finished, being checked |
| `done` | `done` | finished |
| `cancelled` | `done` with a resolution in the "cancelled" list (Won't Do, Duplicate, Cannot Reproduce…) | dropped |

An issue gets a new `status` field (the status id) and keeps `state`, which is now always that
status's category. That makes the change **backward compatible**:

- The view protocol (`ISSUE_STATES`, `hive-view-sdk/src/protocol.ts:262`, `PROTOCOL_VERSION = 1`),
  the widget API, `agent-context.ts`, templates, filters and every existing view keep working on
  `state`.
- `hive ctl set-state X in_progress` still works. It picks the status the workflow marks as that
  category's default (for a Jira-linked issue, the one reachable by a legal transition, §8.2).
- New surfaces read `status` (board columns, the status picker, CLI `--status`).
- A workspace with no `workflow.yaml` gets the six built-in statuses (`status == state`). That's
  how every workspace works today, unchanged.

### 4.2 `.hivemind/workflow.yaml`

```yaml
version: 1
statuses:                         # every status any issue in this workspace may have
  - id: jira:10000                # source-scoped id; never the name (names change, ids don't)
    name: To Do
    category: todo
    color: "#8590a2"              # from Jira's category colour unless overridden
    source: jira
  - id: jira:10001
    name: In Progress
    category: in_progress
    source: jira
  - id: jira:10005
    name: Code Review
    category: in_review
    source: jira
  - id: hive:pr-created           # hive-only status: exists only in hive
    name: PR Created
    category: in_review
    source: hive
    jira: { follow: jira:10005 }  # what Jira should show while an issue sits here (or `stay`)
  - id: jira:10002
    name: Done
    category: done
    source: jira
issueTypes:                       # per-type workflows (Jira allows one per issue type)
  "jira:10004":                   # Bug
    statuses: [jira:10000, jira:10001, jira:10005, hive:pr-created, jira:10002]
    initial: jira:10000
    transitions:                  # learned; see 6.3
      - { id: "21", from: [jira:10000], to: jira:10001, name: Start, screen: false }
      - { id: "31", from: "*",         to: jira:10002, name: Done,  screen: true, fields: [resolution] }
board:                            # Jira board columns, each mapping several statuses
  id: 12
  type: scrum
  columns:
    - { name: "To Do",       statuses: [jira:10000] }
    - { name: "In Progress", statuses: [jira:10001] }
    - { name: "Review",      statuses: [jira:10005, hive:pr-created] }
    - { name: "Done",        statuses: [jira:10002] }
local:                            # hive's rules for hive-only statuses
  onPrOpened: hive:pr-created
  onPrMerged: category:done       # = the done-category status reachable by a legal transition
  onPrClosed: category:in_progress
```

- **Owner.** The Jira plugin writes the `jira:*` statuses and `board`. The person (or the tile's
  editor) owns `hive:*` statuses, `local` and display overrides. Re-discovery never removes a
  status that any issue still uses; it marks it `retired: true`.
- **Several sources.** A workspace can link more than one Jira project or board (a monorepo).
  Status ids are scoped by source and project (`jira:PAY:10001`) when more than one is linked.
- **Validation.** Each status has exactly one category. Each category has at least one status.
  The ids are unique.

### 4.3 What changes in code

- `IssueStateZ` stays as the category enum. Add `status: z.string().optional()`, plus
  `WorkflowZ` and `loadWorkflow(root)` in hive-core with an mtime cache.
- One source of truth for order, labels and colours: `workflowStatuses(root)`. It replaces
  `STATE_ORDER` / `STATE_LABEL` / `STATE_COLOR` in `apps/desktop/tools/issues/src/StateMeta.tsx`,
  plus the CLI arrays (`apps/cli/src/parse.ts`, `format.ts`, `ctl.ts`, `close.ts`, `agent.ts`)
  and `NewIssuePanel.tsx`. Colours per status come from the workflow, and the CSS variables are
  just the fallback.
- **Board view.**
  - Columns are `board.columns`, or one per status when there's no board.
  - Dropping a card on a column with several statuses opens a small status picker.
  - Dropping on a column with no legal transition from the card's status shows why and offers
    the legal targets.
- **Status picker.**
  - With a transition list: the legal next statuses first, then the rest greyed with "no direct
    transition".
  - Without one: every status.
- CLI:
  - `hive update X --status "Code Review"` matches on id or name, case-insensitively.
  - `hive list --status …` and `--category …` filter.
  - `hive workflow show|validate|edit` reads and changes the workflow.
- **Protocol.**
  - Views keep `state`.
  - Add `status` and `statusName` to the issue projection, which stays additive within
    `PROTOCOL_VERSION 1`.
  - Add a `workflow` read (`workspace:issues` permission) so community views can draw real
    columns.

## 5. Core: linking issues to an external tracker and storing them

### 5.1 Frontmatter

```yaml
---
id: PAY-318                    # the Jira key IS the hive id for mirrored issues (5.2)
title: Retry failed webhooks
state: in_review               # category (always derived from status)
status: hive:pr-created
external:
  provider: jira
  source: jira:acme/PAY        # which link (site + project) owns it
  id: "10423"                  # Jira's numeric id: stable across key changes
  key: PAY-318
  url: https://acme.atlassian.net/browse/PAY-318
  type: { id: "10004", name: Bug, hierarchyLevel: 0 }
  remoteStatus: jira:10005     # Jira's status right now (may differ from `status` while in a hive-only status)
  assignee: { accountId: 5b10…, name: Ujjwal Solanki, me: true }
  reporter: { accountId: …, name: … }
  sprint: { id: 87, name: "Sprint 42", state: active }
  priority: High
  estimate: 3
  parentKey: PAY-300           # epic / parent
  remoteUpdated: 2026-10-22T09:14:00.000Z
  syncedAt: 2026-10-24T08:00:12Z
  archived: null               # or { reason: "left scope" | "deleted" | "no access", at }
branch: PAY-318-retry-failed-webhooks
pr: { repo: acme/payments, number: 1187, url: https://github.com/acme/payments/pull/1187, state: open }
github: 1187                   # kept for old readers; mirrors pr.number
assignee: { type: agent, id: claude }   # hive's assignee (who works it here) — NOT Jira's
---
```

Core fixes needed for this to survive (all confirmed on main):

- **Keep unknown keys.** `IssueFrontmatterZ` (`packages/hive-core/src/types.ts:56`) strips them,
  and `serializeIssue` (`storage.ts:339`) writes only known keys. Use `.passthrough()` and write
  unknown keys back. Same for `ConfigZ` (`types.ts:154`), which `allocateId` rewrites on every
  `hive new`.
- **Keep everything in the body.** `parseSections` (`storage.ts:474`) never fills `extra`.
  Activity rows keep only the first line, `who` can't contain spaces, and rows have no ids. Add an
  optional `<!-- id:jira-c-10023 -->` row marker so comments are matched, not duplicated.
- Copy the new fields through `listIssues` and `issueToJson`.

### 5.2 Ids: the Jira key is the hive id

Mirrored issues use their Jira key (`PAY-318`) as their hive id:

- Branches, commits, PR titles and agent prompts all use the key the team already uses. GitHub
  for Jira links them with no extra work.
- Nothing is allocated from `next_id`, so mirrored and local issues never collide.
- **Prefix routing.** The workspace registers `PAY` as an *external prefix*, so `hive show
  PAY-318` from any repo resolves to it. Local issues keep the workspace's own prefix (`HIVEMI-3`).
- **Key rules.** `IssueIdZ` is `^[A-Z][A-Z0-9]{1,9}-\d+`. Jira allows longer keys, and with an
  admin setting, underscores. Widen the regex to `^[A-Z][A-Z0-9_]{1,254}-\d+` for
  external-prefix ids only.
- **Sub-tasks.** They have their own Jira keys and are stored as separate issues with
  `parent: PAY-318`, not as dotted ids. Dotted ids stay for local sub-issues.
- **Key changes.** When an issue moves to another project, the key changes but `external.id`
  doesn't.
  - Sync matches on `external.id`.
  - It renames the file and keeps `aliases: [PAY-318]` so old references still resolve.
  - It writes an activity row.
  - The branch is not renamed.

### 5.3 Where mirrored issues live

`.hivemind/` is committed in many repos (this one commits `config.yaml`). If teammates each synced
their own "mine" scope into committed files, they would fight over merge conflicts. So:

- Mirrored issues live in **`.hivemind/mirror/<source>/`**.
  - `hive init` and the plugin add that folder to `.gitignore`.
  - Each machine keeps its own mirror, and Jira holds the shared truth.
  - `listIssues` reads `issues/` and `mirror/**`.
- Setting `mirror.commit: true` puts them in git instead, for single-person repos that want
  history.
- Sync state lives in `.hivemind/sync/<source>/`, gitignored:
  - `ledger.json`: `external.id → hive id`, plus the last remote `updated` and a hash of what was
    last written each way.
  - `schema.json`: the discovered workflow and fields.
  - `queue.jsonl`: pending pushes.
  - `lock`: single-writer.
- **One writer per workspace.** The service takes `lock` (pid + machine + heartbeat). With `hive
  share` / `hive host`, only the host syncs and guests see the result.

### 5.4 `hive ingest`: the one write path for every source

`hive ingest --source jira:acme/PAY [--dry-run] --json < records.ndjson`

Each line is a **normalised record**: provider-neutral fields plus `external.*`. Ingest upserts by
`(source, external.id)`:

1. **New** → it creates the mirrored file.
2. **Known, and remote `updated` is newer than the ledger** → it applies the fields Jira owns,
   which are listed in §8.1.
3. **Status:** it applies the conflict rule in §8.3.
4. **Unchanged hash** → it does nothing.

It reports `{created, updated, unchanged, conflicts, archived}`.

The REST service, the MCP transport and an agent holding a Jira connector all write through
ingest. Only the *reading* differs between them, so correctness lives in one place, with tests.

## 6. Discovery: learning a Jira

Discovery runs on connect, every 6 hours, and immediately whenever an issue comes back with a
status, issue type or field the schema doesn't know. The results go in `sync/<source>/schema.json`,
and `workflow.yaml` is regenerated from it.

### 6.1 What is discovered (REST v3; DC uses v2 equivalents)

### 6.2 Adapting to each kind of Jira

| Shape | How it's handled |
|---|---|
| Company-managed, shared workflow scheme | Statuses per issue type from `/project/{key}/statuses`; several types can share one workflow |
| Team-managed | Statuses are project-scoped and may share names with other projects; ids keep them apart. The "Sprint" and "Story point estimate" fields have different ids, so they're found by schema, not by name. |
| Scrum board | The scope can be the active sprint(s); columns come from the board; future sprints are browsable |
| Kanban board | No sprints. Scope = board filter JQL + board columns. Kanban's "Backlog" column maps to the `backlog` category. |
| No board / Jira Work Management | Columns = statuses ordered by category, then name; scope = project JQL |
| Several boards on one project | The person picks one in setup and can switch it |
| Different workflow per issue type | `issueTypes` in `workflow.yaml`; the picker shows only that type's statuses |
| Global transitions ("any status → Done") | `from: "*"` |
| Transition screens / required fields / validators | Learned from `expand=transitions.fields`; hive asks for the required values (§8.2) |
| Conditions (e.g. only the assignee can transition) | Not visible up front; a refusal is reported in words, and the move is undone locally |
| Data Center 8.x / 9.x | REST v2 (`/rest/api/2`), PAT bearer auth, wiki-markup rich text, no `/search/jql` (uses `/rest/api/2/search` with `startAt`), no team-managed projects |
| Hierarchy above epic (Plans / Premium) | `hierarchyLevel ≥ 2` types are mirrored as parents and shown read-only |

### 6.3 The transition graph

When admin access allows it, the full workflow is read with `/workflows`. Otherwise the graph is
**learned**:

- Each pulled issue's `GET transitions` result is cached under `(issueType, fromStatus)` with a
  TTL of 24 hours, and again after any refused transition.
- Pathfinding (§8.2) uses the cache.
- An unknown edge triggers one live `GET transitions` for that issue before anything is decided.
- Live data always wins over the cache, because conditions are per issue and per user.

### 6.5 Rich text

- **Cloud v3** sends descriptions and comments as **ADF**, which is converted to markdown.
  - Candidates to check in P-R: `adf-to-md`, `@atlaskit/editor-markdown-transformer`, or our own
    small converter.
  - Panels, mentions, media and status lozenges become plain-text equivalents.
  - The original ADF is kept in `sync/<source>/adf/<id>.json`, so a later push never has to
    round-trip lossily.
- **DC v2** sends wiki markup, converted with a wiki → markdown converter.
- **Pushes.** Comments go up as ADF built from markdown. **Descriptions are never pushed by
  default**: Jira owns them, and lossy round-trips damage them.

## 7. Pulling: scope, cadence, correctness

### 7.1 Scopes (a setting, editable in the tile)

| Scope | JQL (built per source) |
|---|---|
| **`mine`** (default) | `<base> AND assignee = currentUser()` |
| `mine+unassigned` | `<base> AND (assignee = currentUser() OR assignee is EMPTY)` |
| `all` | `<base>` |
| `jql` | the person's own JQL, AND-ed with the project |

`<base>` comes from the board type:

- **Scrum:** `project = PAY AND sprint in openSprints()`. A setting adds `OR sprint in
  futureSprints()`, or the backlog.
- **Kanban:** the board filter's JQL, with `statusCategory != Done OR updated >= -14d` so finished
  work fades out instead of piling up.
- **No board:** `project = PAY AND statusCategory != Done`.

Always add `AND issuetype not in (<excluded types>)`. By default this is empty. Epics are pulled
as parents, not as work items.

**What happens to issues that are not mine**
- When the scope is wider than `mine`, those issues are mirrored too, but marked
  `external.assignee.me: false`.
- The board's **assignee filter** defaults to **Me**. Its options are **Me**, **Unassigned** and
  **Anyone**, plus a person picker, and the choice is remembered per workspace.
- Cards not assigned to me show the assignee's avatar or an "Unassigned" chip.

**Browse without importing**
- The tile's **Browse** tab runs any scope or JQL live and shows the results without writing
  files.
- **Track** imports one issue, and so does starting work on it (§10).
- This avoids a mirror full of issues nobody here will touch.

**Shrinking the scope** (e.g. all → mine)
- Mirrored issues that are no longer in scope are **archived**: hidden, not deleted.
- The exception is issues with local work: a branch, a PR, or agent activity. Those stay visible
  with a "not in scope" chip.

### 7.2 Cadence

- **Incremental poll** every 60–300 s. It is adaptive: faster while the app is focused, slower
  when idle or when rate-limited.
  - JQL: `<scope> AND updated >= "<ledger high-water − 2 min>" ORDER BY updated ASC`.
  - It uses `POST /rest/api/3/search/jql` and pages with `nextPageToken`.
  - **Always pass `fields`**: it defaults to `id` only. Pass only what §6.4 needs.
  - Search embeds at most about 20 comments and changelog entries per issue, so comments and
    history come from their own endpoints.
  - Data Center uses `/rest/api/2/search` with `startAt`.
- **Full reconcile** every 6 hours and on demand.
  - It fetches every id in scope with only `fields=updated,status,assignee` (`maxResults`
    up to 5000 for id-only pages).
  - It compares the result with the ledger to find issues that **left scope**, were **deleted**,
    or **lost access**, because an incremental poll never sees an issue that disappeared.
  - Ledger ids missing from scope go through `POST /rest/api/3/issue/bulkfetch` in batches of
    100. That call silently omits issues that are missing or forbidden: an omitted issue counts
    as deleted or no access (archived with that reason). A returned issue under a different key
    has moved (§5.2). A returned issue still under its key has only left scope.
  - `POST /rest/api/3/jql/match` re-checks scope membership cheaply.
- **Comments:** fetched with `GET /issue/{key}/comment`, only for issues whose `updated` changed.
- **Changelog:** `POST /rest/api/3/changelog/bulkfetch` with `fieldIds: [status, assignee]` for
  the changed ids. It's only used to decide status conflicts (§8.3), not to rebuild history.
- **On demand:**
  - Sync now (tile).
  - `hive ctl plugin call @dip497/jira sync`.
  - Touching `.hivemind/sync/<source>/request`, which works even with the tile closed. Today a
    service can't answer `plugin call` (`docs/design/plugin-control-2026-10-16.md`).

### 7.3 Correctness traps

- **Time zones in JQL.** JQL date literals are read in the *user's profile time zone*, to the
  minute. Format the high-water mark in `myself.timeZone` and overlap it by 2 minutes. Ingest's
  hash check makes the overlap free.
- **Pagination.** Use the token-based `/search/jql`. The old `startAt` search on Cloud
  (`/rest/api/3/search`, `/rest/api/2/search`) returns **410 Gone** (CHANGE-2046). Page tokens
  expire after 7 days. There is no total count.
- **Eventual consistency.** Pass `reconcileIssues` (up to 50 ids) to make sure our own writes
  show up when we read straight after pushing.
- **Field ids** differ between sites and between team-managed projects. Never use a custom field
  by name after discovery.
- **Clock skew:** compare Jira's `updated` with Jira's `updated`, never with the local clock.
- **Issue security levels / restricted issues:** a 404 on a known issue means "no access", not
  "deleted". The mirror keeps the last copy as archived, with that reason.
- **Archived projects and issues:** treated as left scope.

## 8. Pushing to Jira (opt-in per source: `push: off | status | status+comments | full`)

### 8.1 Field ownership

| Field | Owner | Pushed when |
|---|---|---|
| title, description, type, priority, sprint, labels, components, parent, links | Jira | never. A local edit to these is refused for mirrored issues, with "edit in Jira" (opens the URL) |
| status | both | `push ≥ status` (§8.2, §8.3) |
| assignee | Jira | only through the start-work guard's "Assign to me" (§10), with `push ≥ status` |
| comments by people in hive, agent plan/summary, PR opened/merged | hive | `push ≥ status+comments`. Agent progress chatter is never pushed; a per-row-type allowlist lives in settings. |
| acceptance-criteria ticks | hive | `push = full`, and only when AC lives in a checklist the transport can write without losing anything |
| PR link | hive | remote link `POST /issue/{key}/remotelink` with `globalId: "github-pr:<org>/<repo>#<n>"`, an idempotent upsert (§11.4). Jira has no public API that reads the PRs GitHub for Jira linked (dev-status is internal), so hive always writes its own link and reads PR state from GitHub. |
| sync metadata | hive | an entity property `PUT /issue/{key}/properties/hivemind` (`{hiveVersion, branch, pr, by}`, ≤32 KB; needs *Edit issues*), read back through the `properties=hivemind` search parameter, so teammates' installs see the work is underway. P-R checks whether writing it bumps `updated`; if it does, the ledger ignores our own property writes. |

### 8.2 Status → transition

Jira can't set a status directly. To move to target status `T`:

1. **Hive-only target.** If `T` is hive-only (`source: hive`), set it locally. Then, if
   `jira.follow` names a Jira status, apply steps 2–5 for that status instead. If it says `stay`,
   Jira isn't touched.
2. Fetch the issue's live transitions.
3. If one goes directly to `T`, use it.
4. Otherwise find the **shortest path** in the learned graph, at most 3 hops. Each hop's
   transitions are fetched live before the hop is taken.
   - Auto-taking multi-hop paths is a setting, default on for paths that need no screens.
   - For other paths the person is shown the path and confirms it.
5. **Screens / required fields.** `hasScreen` tells whether a screen applies, and
   `transitions.fields[*].required` lists what it needs (e.g. resolution). Fields are fetched
   with `expand=transitions.fields`.
   - Hive shows a form built from the field metadata, pre-filled from per-transition defaults in
     settings.
   - `resolution` is sent only when it appears in `transitions.fields`.
   - A required field that isn't on the screen comes back as a 400 `errors{}`. Its message is
     shown, and the field is remembered for next time.
   - Agents can't fill screens. Their move stops at the last step that needs none and is flagged
     for the person.
6. **Refused (validator or condition):** the local status is put back, the issue's activity gets
   Jira's error message, and a toast offers to open it in Jira.

Pushes are queued (`sync/<source>/queue.jsonl`), debounced 5 s, and merged per issue: the last
target wins. A failed push is retried with backoff and survives restarts. While a push is pending,
the card shows a "syncing" mark.

### 8.3 Status conflicts

Both sides changed status since the last sync (the ledger holds the last synced remote status and
the last local change):

- **Remote moved, local didn't** → take the remote status.
- **Local moved, remote didn't** → push.
- **Both moved to the same status** → nothing to do.
- **Both moved to different statuses:**
  - If the local move was *only* into a hive-only status whose `follow` equals the new remote
    status, they agree.
  - Otherwise this is a **conflict**: the card gets a mark, and the tile's Conflicts list shows
    both sides with "Keep Jira" / "Keep hive". The default after 24 h is Keep Jira.
- **Remote reached `done` or `cancelled` while local work exists** (branch / PR) → take the remote
  status. Tell the person; never close their PR.

## 9. Transports

All transports implement one interface inside the plugin:

```ts
interface JiraTransport {
  capabilities: { workflowGraph: boolean; changelog: boolean; adf: boolean; fieldsMeta: boolean; agile: boolean; entityProps: boolean; push: boolean };
  discover(): Promise<Schema>;
  search(jql: string, fields: string[], pageToken?: string): Promise<Page<RawIssue>>;
  issue(idOrKey: string): Promise<RawIssue | Gone>;
  comments(key: string, since?: string): Promise<RawComment[]>;
  transitions(key: string): Promise<Transition[]>;
  transition(key: string, id: string, fields?: object): Promise<void>;
  assign(key: string, accountId: string | null): Promise<void>;
  comment(key: string, markdown: string): Promise<{ id: string }>;
  remoteLink(key: string, link: RemoteLink): Promise<void>;
}
```

The sync engine (scope, ledger, ingest, queue, conflicts) never knows which transport it's
talking to. Features a transport can't support are turned off in the UI, with the reason shown.

### 9.1 REST (default)

- **Cloud, API token (default).**
  - Classic: Basic `email:token` against `https://<site>.atlassian.net`.
  - Scoped (preferred; Atlassian is deprecating unscoped tokens): Basic `email:token` **only**
    against `https://api.atlassian.com/ex/jira/{cloudId}`. The site URL returns 401 for these.
    The wizard looks up the cloudId and asks for these scopes: `read:jira-work`,
    `write:jira-work`, `read:jira-user`, plus the board and sprint read scopes.
  - Tokens expire after 1–365 days (since 2024-12-15). The token's age can't be read through the
    API, so the wizard asks for the expiry date, and the tile warns 14 days before it.
  - **API-token traffic is exempt from the points quota**; only the burst limits apply. That's
    the main reason it's the default.
- **Cloud, OAuth 2.0 (3LO).** **Deferred.**
  - It needs a client secret for both the code exchange and refresh, and **Cloud has no PKCE**
    (ECO-283).
  - Its traffic also counts against an app-wide 65k points/hour pool shared by every user.
  - It needs a secret-holding broker. The MCP path below gives "sign in with Atlassian" without
    one.
- **Data Center:** a Personal Access Token as `Bearer` (Jira 8.14+), REST v2 plus
  `/rest/agile/1.0`. Rich text is wiki markup, search uses offset paging, and users are
  usernames. DC reaches end of life on 2029-03-28, so it's supported, but Cloud comes first.
- **Rate limits.**
  - Burst limits: GET/POST 100/s, PUT/DELETE 50/s per endpoint.
  - **Per-issue writes: 20 per 2 s and 100 per 30 s.** The push queue merges writes per issue
    and spaces them out.
  - Honour `Retry-After`. Read `RateLimit-Reason`: a quota reason pauses everything until the
    reset; a burst reason slows only that endpoint.
  - `X-RateLimit-NearLimit` turns the poll rate down.
  - At most 4 requests in flight. Backoff is jittered (×0.7–1.3), starting at 2–5 s, capped at
    30 s, with 4 retries, for idempotent requests only.
  - The tile shows "rate-limited, next try 14:02".

### 9.2 MCP: the Atlassian Rovo MCP server (Cloud only)

From research on 2026-10-24; check again in P-R.

- **Endpoint.** `https://mcp.atlassian.com/v2/mcp?tools=all` (Streamable HTTP), which lists tools
  flat instead of through discover/execute. `/v1/sse` is retired, and on 2027-03-01 v1 traffic
  moves to v2 tools. Tool *names* changed between v1 and v2 once already, so the transport finds
  tools by capability through `tools/list`, using a name table it can update.
- **Auth.**
  - OAuth 2.1 with dynamic client registration and PKCE, through a **loopback redirect**:
    `http://127.0.0.1:*/**` is in Atlassian's default allowlist for MCP clients. That gives "sign
    in with Atlassian", and no developer app is needed.
  - Or an **API token**, which an org admin must turn on. It is sent as Basic `email:token` with
    an explicit `cloudId`.
- **Client.** The official TypeScript MCP SDK (`@modelcontextprotocol/client` v2, or
  `@modelcontextprotocol/sdk` v1), using `StreamableHTTPClientTransport` and an
  `OAuthClientProvider`. Tokens go into `secret` storage.
- **Tools used:**

  | Purpose | Tools |
  |---|---|
  | Site and user | `getAccessibleAtlassianResources`, `getJiraCurrentUser` |
  | Search and fetch | `searchJiraIssuesUsingJql`, `getJiraIssue` |
  | Statuses and transitions | `listJiraStatuses`, `listJiraIssueTransitions`, `transitionJiraIssue` |
  | Comments and changelogs | `listJiraIssueComments`, `addOrEditJiraIssueComment`, `listJiraIssueChangelogs` |
  | Boards and sprints | `listJiraBoards`, `getJiraBoardConfig`, `listJiraBoardSprints`, `getJiraBoardIssueData` |
  | Fields | `getJiraIssueTypeMetaWithFields` |
  | Writes | `editJiraIssue` (assign), `createJiraIssueRemoteIssueLink`, `get`/`editJiraEntityProperty` |

- **Limits that make it second choice:**
  - **Rich text is markdown only**; ADF requests are ignored. So `capabilities.adf = false`, and
    description pushes are off.
  - **Output shape.** It is semi-structured. `structuredContent` was seen withheld from clients
    whose `clientInfo.name` isn't recognised. Every response is validated against our own schema,
    and anything that doesn't match fails loudly instead of being guessed at.
  - **The full workflow graph needs the admin-gated `manage_jira` tools**, so the learned graph
    (§6.3) is the norm here.
  - **No bulk changelog and no fields search.**
  - **Rate limits.** Hourly limits by plan aren't officially published. 429s have been reported at
    about 20 parallel calls, so cap concurrency at 3.
  - **Credits.** `search` (Rovo semantic search) costs Rovo credits, so it is **never used**; JQL
    tools only.
- **When to choose it:** the org disallows API tokens but has OAuth MCP enabled, or the person
  wants "sign in with Atlassian".

### 9.3 MCP: self-hosted `sooperset/mcp-atlassian` (Cloud + Data Center)

- MIT licence, Python (uvx/Docker), stdio transport, JSON text output.
- It has bulk changelogs, field search, agile tools and development info.
- Hive never bundles it. If the person has it installed, it's a transport choice, which is mainly
  useful for Data Center sites that block direct REST from desktops.
- Same capability flags as §9.1.

### 9.4 Agent with a Jira connector (no service)

- An agent tile that holds the Atlassian connector (Claude, Cursor, …) reads Jira over MCP and
  writes **only** through `hive ingest`. The skill `jira-import` (shipped with the plugin) carries
  the record format and the rules.
- Good for: a one-off import, "pull epic PAY-300 and its children", triage. Not continuous sync:
  it costs tokens, it isn't scheduled, and issue text could carry prompt injection.
- **Guardrails:**
  - Ingest validates every record.
  - An agent can't push to Jira through ingest; pushes go through the service or the person.
  - Ingest doesn't do anything an issue's text tells it to.

### 9.5 Why no webhooks

- A desktop app has no public URL.
- Dynamic webhooks are only for OAuth / Connect apps: they expire after 30 days, there are 5
  per user, and they need public HTTPS with a trusted certificate.
- A relay (a Forge app, or a tunnel) would add a hosted piece and an account to run it.
- Polling with incremental JQL is cheap enough at sprint scale.
- **Later:** a `hive host` on a reachable server could take webhooks and treat each one as a hint
  to poll now. It would never be the source of truth.

## 10. The start-work guard

`checkStartWork(issueId, actor)` lives in core and runs before every way of starting work:

- the UI's "Work on this";
- dragging to an `in_progress`-category status;
- `hive ctl set-state … in_progress` or `hive update --status <in-progress status>`;
- `hive ctl spawn --issue`;
- `hive ctl workflow` with issues as items.

It **re-fetches the issue live** when the last sync is more than 60 s old, then checks:

| # | Check | Severity | Offered actions |
|---|---|---|---|
| 1 | Jira assignee is **nobody** | warn | **Assign to me and start** · Start without assigning · Cancel |
| 2 | Jira assignee is **someone else** | warn (strong) | Start anyway (posts "picked up in hivemind by …" if comments are pushed) · Assign to me and start (needs `ASSIGN_ISSUES`) · Cancel |
| 3 | Status category is already `in_progress`, by someone else | warn | as #2 |
| 4 | Status category `done` / `cancelled` | warn | Reopen (if a transition exists) · Cancel |
| 5 | Not in an active sprint (backlog / future sprint) | info | Start anyway · Cancel |
| 6 | Blocked by an unresolved issue (`is blocked by` link) | warn | Start anyway · Open blocker · Cancel |
| 7 | Flagged / impediment | warn | Start anyway · Cancel |
| 8 | No permission to transition (`TRANSITION_ISSUES`) or be assigned (`ASSIGNABLE_USER`) | info | Start locally only (no Jira push) · Cancel |
| 9 | Sub-task whose parent is done, or epic closed | info | Start anyway · Cancel |
| 10 | Another hive install is already on it (entity property `hivemind.branch` from someone else, §8.1) | warn | Start anyway · Cancel |
| 11 | An agent tile here is already working this issue | block | Focus that tile · Cancel |

**Surfaces**
- **UI:** one dialog listing every finding, with the actions above. Checking "Don't warn me for
  unassigned issues in this workspace" turns off #1 only.
- **CLI / agents:** refuses with exit **7**, `code: "NEEDS_CONFIRM"` and `warnings: [{check,
  message, actions}]`.
  - `--assign-me` does "Assign to me and start".
  - `--ack <check,…>` acknowledges specific checks, for example `--ack unassigned`.
  - `--force` acknowledges every warn-level finding. Block-level findings can't be forced.
  - The agent skill says: **ask the person, never `--force` on your own.**
- **`hive ctl workflow`:** runs the guard on every item first. Items with findings are left out
  and listed under `skipped[]`, unless the caller passed `--ack`.

**Who is "me"**
- Jira's assignee is the **person** whose token or OAuth the sync uses (`myself.accountId`).
- Hive's `assignee` is the **agent** doing the work.
- "Assign to me" sets the Jira assignee to the person. Agents never become Jira assignees.

## 11. Branch, worktree, PR

### 11.1 Start

After the guard passes:

1. Creates or reuses the branch `<KEY>-<slug>` (`settings: branchTemplate`, default
   `{key}-{slug}`).
2. Creates the worktree with `worktreeCreate` (used in `apps/desktop/src/main/index.ts` on main)
   and opens it as a worktree frame.
3. Writes `branch:` on the issue.
4. Moves the issue to the workflow's start status (§8.2) and pushes it.
5. Spawns the agent in that frame with `tile.issue = "<KEY>"`, a structured field rather than
   just prompt text.
6. Gives the agent a prompt built from the issue: description, AC and links. It ends with the
   §11.2 contract.

### 11.2 Agent contract (replacing "Do NOT push" in `hive-core/src/templates.ts`)

- Commit as `<KEY>: …`, and end with `hive ctl complete <KEY>`.
- `complete` checks:
  - the tree is clean and the branch has commits ahead of base;
  - the AC are ticked, or there's an `--ac-note` explaining why not;
  - the local tests, if `config.yaml` names a check command.
- Then, by workspace policy:

```yaml
# .hivemind/config.yaml (needs ConfigZ to keep unknown keys, §5.1)
on_complete: pr          # pr | draft_pr | review   (default review = today's behaviour)
pr_base: main
pr_gate: none            # none | approve  (approve blocks on `hive ctl open-review` before the PR opens)
cleanup: ask             # ask | auto | never  (worktree + local branch after merge)
```

### 11.3 `hive pr`

| Command | Does |
|---|---|
| `hive pr create <KEY> [--draft] [--base]` | Pushes `-u`, then runs `gh pr create`. Title: `<KEY>: <title>`. Body: summary, AC checklist, Jira link, agent's completion summary. Writes `pr` + `github`, then moves to `local.onPrOpened`. |
| `hive pr status <KEY>` | `gh pr view --json state,mergedAt,reviewDecision,statusCheckRollup,url` |
| `hive pr sync` | The watcher's single pass, for scripts |

- **Auth:** `gh` is the auth. When `gh auth status` fails, the command says how to fix it and moves
  the issue to the `in_review` category with a note. Nothing hangs, and no GitHub tokens are
  stored.
- **Remote tiles:** a tile on a remote machine uses that machine's `gh`, the way `git` runs there
  (`remote/git.ts`).

### 11.4 PR watcher (host side, so it runs under `hive host` too)

Every 3 minutes it checks every issue with `pr.state: open`, batched in one `gh api graphql` query:

| PR event | What hive does |
|---|---|
| **merged** | moves to `local.onPrMerged` (pushed as a transition), offers cleanup |
| **closed, not merged** | moves to `local.onPrClosed`, with a note and a notification |
| **changes requested** | stays put; the card shows a badge; "Address review" spawns an agent in the same worktree with `gh pr view --comments` |
| **checks failing** | badge; "Fix CI" does the same as above with the failing logs |

The remote link on Jira carries the PR URL. When the PR is merged, the link's status is updated
to resolved.

## 14. Security and privacy

- **Tokens** are only ever in `secret` storage. They never appear in issue files, logs (the service
  log redacts `Authorization`), `settings.json` or the agent's environment.
- **Agent tiles get no Jira credentials.** Agents act on Jira only through hive commands, which
  the service carries out.
- **Mirrored issue text is untrusted.** It is shown, never run. When it goes into agent prompts it
  is fenced as quoted material, and the skill says so.
- **Mirrors are gitignored by default** (§5.3), so private ticket text isn't pushed to a repo by
  accident.
- **Pushes** are opt-in, and every write to Jira is recorded in the issue's activity
  (`who: hive→jira`).

  - JWM with no board;
  - DC v2 with wiki markup;
  - screens with required resolution;
  - a refusal by a condition;
  - multi-hop transitions;
  - a moved key;
  - a deleted or restricted issue;
  - 429s.

  The sync engine's unit tests run against it, and the transport contract tests run against both
  the fake and a recorded MCP session.
- **Ingest property tests:** applying any sequence twice = applying it once. A kill and restart at
  any point produces no duplicates and no loss.
- **Guard tests:** every row of §10, from the UI and the CLI, including the exit codes and the
  `--ack` behaviour.
- **e2e (Playwright):**
  1. Wizard → first sync → board columns match the fixture's board.
  2. Drag across a screen transition → form → push.
  3. Start an unassigned issue → dialog → assign → spawn.
  4. Complete → PR (with a `gh` shim) → merge → Done.
- **Live smoke** (manual, before release): a real Cloud sandbox site and, when available, a DC
  instance. The result goes in the PR description.
