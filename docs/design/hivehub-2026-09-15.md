# HiveHub — the plugin registry

Status: proposed. 2026-09-15.

A separate repository and a separate deploy: a registry service where anyone signs in with
GitHub, publishes a plugin, and sees how many people installed it. The app keeps working if
it is down.

## What we already have that a registry usually has to build

Three things are already true, and the design is mostly a matter of not throwing them away.

**Installs are pointers, not uploads.** `plugins/index.json` lists a plugin's files with a
SHA-256 each; `plugin-catalog.ts` fetches them from the publisher's own host and refuses any
file whose hash moved. The registry never holds the bytes. That removes storage, blob
moderation, backup and restore, and the obligation never to lose data — all of which a
registry that hosts artifacts has to build and keep running.

**A plugin cannot express arbitrary behaviour.** An agent is a declarative manifest and
`manifest.ts` gates every capability in it; a view is sandboxed code on its own origin with
no node and no network. The set of things a published plugin can even ask for is closed, and
`agentDisclosures(def)` already enumerates it in a sentence each. A registry whose content is
free-form prose or arbitrary code has to scan uploads to find out what they do. Ours does not
have to find out — the manifest says, in a vocabulary the validator enforces.

**One validator.** The site must never advertise something the app would refuse. So HiveHub
validates with `@hivemind/agents` itself, untrusted, the same call the app makes.

## What we are deliberately not building

Studied the largest comparable registry in this space. Most of its code is consequence, not
feature — worth naming so we do not re-derive each one by getting hurt first.

| Their machinery | Why they needed it | Why we do not, yet |
| --- | --- | --- |
| LLM upload scanners, abuse scoring, autoban, publish limits | Free-form content that an agent will execute — a prompt-injection channel | Closed manifest vocabulary. The validator is the gate; disclosures are the disclosure |
| Artifact storage plus backup and restore to GitHub | They are the store of record | The publisher's repo is the store of record. Losing our database loses rankings, not plugins |
| Stars, comments, leaderboards, badges | Community at scale | 18 plugins and no community. Every one of these is a spam surface with a moderation bill |
| Reserved handles, reserved slugs, ownership transfer | Land rush on a global flat namespace | Same namespace, but no rush yet. See "the ceiling" below |
| Login-gated CLI telemetry, opt-out env var, decrement-on-account-deletion | Counting installs client-side | Count server-side at the resolve endpoint. No login, no client telemetry, no PII |
| Parallel publish, changelog and backup paths per content type | Three content types grown one at a time | One `plugins` table with a `type` column, one publish path. The manifest differs; the record does not |

The rule behind the table: **do not add a content type or a social signal that reopens the
firehose.** The small moderation surface is a property of the format, and it is only kept by
refusing formats that give it up.

## Shape

```
hivehub/            Astro (SSR) + Cloudflare Workers + D1, Drizzle
  src/pages/        the catalog, reusing workspace.css, Shell.astro and mark.ts verbatim
  src/api/v1/       index.json, plugins, resolve, publish
  src/db/           schema.ts
```

Astro because the catalog pages already exist on the docs site and are the prototype — the
tokens, layout and icon renderer move across as files. Cloudflare because a registry at this
size is a read-mostly SQLite database behind a CDN, and D1 is that with one deploy command.

### The API

`GET /api/v1/index.json` is byte-compatible with today's `plugins/index.json`, so pointing
`HIVEMIND_PLUGIN_INDEX` at HiveHub is the entire client change. Everything else is additive:
`GET /plugins?q=&type=&sort=`, `GET /plugins/:id`, `GET /plugins/:id/resolve` (counts),
`POST /plugins` (publish).

### A mirror, not a backup

A cron writes the same `index.json` back to the hivemind repo. `DEFAULT_PLUGIN_INDEX` stays
pointed at `raw.githubusercontent.com` as the fallback, so HiveHub being down degrades
discovery and nothing else. One generator, two URLs, no second source of truth.

### Counting installs

The resolve endpoint counts, deduped on a salted hash of `(ip, plugin, day)` with the salt
rotated daily and the hash never stored beyond the day. No account, no client telemetry, no
opt-out to honour, nothing to delete when an account is. The page says exactly that method
next to the number, because an install count that does not say what it counted is decoration.

### Publishing

Sign in with GitHub. Paste a repository URL. The server fetches the manifest, validates it
untrusted, and **verifies through the GitHub API that the signed-in account can write to that
repository** — that check, not the URL, is what makes the owner real. Then it shows you the
disclosures it computed from your own manifest and asks you to confirm them. Listed.

`hive agents publish` comes after the web form, on GitHub's device flow. One client at a time.

Reading and installing never require an account.

### Ownership and the ceiling

First come, first served on a bare id, `RESERVED_AGENTS` blocked, no duplicates — which is
what the current schema enforces anyway, since it dedupes on `type:id`. Transfer is a row
update by hand.

## Order

1. `@hivemind/agents` published to npm. Nothing else can be honest without it.
2. Read-only HiveHub: catalog, detail, search, seeded from `plugins/index.json`.
   `/api/v1/index.json` live, counts running.
3. GitHub sign-in and the publish form.
4. `hive agents publish`, profile pages, report-and-yank.

Steps 1 and 2 are the ones that change anything: after them the app installs from a service,
and the number under a plugin is real.
